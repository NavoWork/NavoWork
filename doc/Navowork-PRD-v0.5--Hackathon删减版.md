## 0. 融合原则、范围和不变项

### 0.1 本次修正结论

1. **W1 是「询盘评估 → 产品方案 → 可核价规格 → BOM/成本 → 初步报价与打样准备」。** 是否做竞品研究与 AI 生图，取决于客户究竟是在 OEM 来图定制、现款 ODM 改造还是新款共同开发；不能要求所有询盘重新设计。
2. **W2 是「商务协商 / 实物打样反馈 / 客户 PO → 条款与版本确认 → PI/订单资料准备」。** 三种事件可分别进入，不要求样品反馈和 PO 同时存在；可在不同时间反复调用。
3. **变更联动是工作台共用底座，绝非 W2 的附属步骤。** 从 W1、W2 或直接文件编辑进入，处理机制一致。
4. **不强加“先全部样品批准，再做 PI”的固定顺序。** 客户可能先要求 PI 办理定金，也可能先打开发样。样品/规格的最终量产批准、合同成立、付款保障与 PI 文件制作是不同业务事件。
5. **Wiki 关联用于知识理解和影响候选发现，不是订单事实主库、价格来源的最终证明或自动改文件的授权。**

### 0.2 必须保留的产品能力

| 能力 | 产品要求 |
| --- | --- |
| 连续业务上下文 | 客户询盘、设计、规格、BOM、成本、报价、打样与 PO/PI 关联在同一 Case；后续复用已确认内容 |
| 工作台与 Agent | 保留对话 + 成果区为默认布局，用户可自然语言提出目标，也可直接编辑文件，不强制操作 Job 管理模块 |
| 通用文件编辑器 | 真实编辑文档正文、图片、表格和工作表及支持的公式；编辑触发相关业务检查 |
| 原生多格式导出 | 实际 DOCX、XLSX、PDF；产品概念图 PNG/JPEG；页面与文件来自明确的同一内容版本 |
| 竞品分析 | 基于少量有来源、时间和适用范围的资料提供比较、观察和候选设计建议 |
| AI 美工与生图 | 生成概念模拟图、支持用户反馈修改，形成可编辑客户设计提案；明确非工程图和非实物样品 |
| BOM 识别与核价 | 读取简易 XLSX 或 VLM 识别清晰表格图像，逐行核对，并由程序计算成本和报价 |
| 全链路变更联动 | 从用户指令、客户反馈、文档编辑、上传资料和设计调整触发，传播至相关成果和导出件 |
| 来源/版本/确认保护 | 保留原文、原文件、批准对象、内容版本和旧交付；新草稿不自动覆盖已批准事实 |
| 校验与反馈 | 对本次目标区分成功、待补充、待复核和失败；给出定位与下一步，并可在原 Case 继续 |

### 0.3 不进入本参赛版的范围

不新建完整 CRM、企业部门权限后台、多人实时共同编辑、全网实时竞品采集、通用插件市场、复杂长周期任务调度、多币种全球定价系统、多供应商自动采购询价、多款并行报价引擎。稳定的现有首页/Tab 可以保留，不因本稿强制重做。

不进行真实客户获客、信用调查、邮件实际发送、签署合同、实物打样、寄样、银行收款核验、采购下单或量产。SOP 6–7（生产验货之后的出运、收款、售后）不在范围。支持简单 XLSX 与基础文档编辑并不承诺复杂宏、任意外部公式、复杂排版无损兼容。

### 0.4 核心用语必须区分

- **客户请求 / Requested**：客户提出希望变更，不表示工厂可做或双方已确认。
- **候选 / Proposed**：设计、规格、报价或文件的新草稿，允许继续修改。
- **可核价规格基线**：当前产品方案达到可以核算特定成本范围的程度，**不是量产最终技术规格**。
- **目标估价 / 条件性报价 / 可审核正式报价草稿**：成本与证据成熟度不同，不可混写成最终报价。
- **接受 / Accepted**：客户对具体方案、规格或商业条件有可回溯的接受证据；不能跨版本泛化。
- **样品批准 / Sample Approved**：对具体实物样品及其对应规格版本的批准；不等于看过或喜欢概念图。
- **已同步 / Synced**：本轮已纳管工作稿与当前事实一致；**不等于客户批准、已发送、已签约或已开工**。

## 1. 产品定位、用户与操作模型

**EasyWork 是将客户需求变成可看、可改、可核价、可交付的包袋产品与商务成果，并在需求变化后持续修订相关成果的一人 AI-Native 工作台。**

目标用户是中小 B2B 包袋出口企业的外贸业务员、业务跟单员、兼任设计沟通与核价的小团队成员。用户负责业务目标、选择方案、商业判断与真实确认；Agent 负责理解资料、调取知识和来源、组织工具、制作工作成果、核价、检测差异、推进可自动执行的修订。

核心操作方式是：

- 用户可以粘贴客户询盘，直接说“帮我准备一个报价与设计提案”。
- 用户也可以直接进入已有 Case，上传客户图、完整 Tech Pack、供应商 BOM、样品反馈或 PO，跳过不相关步骤。
- 用户可以在已有 BOM 的单元格直接修改用量，在文档中修改规格，在对话中要求“LOGO 从 5 cm 改成 6 cm”；这些变化统一进入变更链。
- 结果是实际可编辑、可验证、可导出的成果，不是只更新任务状态，也不是只生成聊天文字。

**一个 Case 是业务容器；W1/W2 是可复用的业务能力而不是只能运行一次的状态机。** 当前正在执行的工作可由系统内部记录 Run/版本，不要求用户手动创建 Job 才能开始。

产品价值的四个可观察维度：连续完成工作；直接操作真实文件；一处变更全链路关联更新；明示未完成和审批边界以免旧文件被误认为当前有效成果。

## 2. 前五个 SOP 的业务覆盖及真实边界

| SOP | 工作台承担的数字工作 | 核心业务成果 | 不能越过的边界 |
| --- | --- | --- | --- |
| 一、客户开发与询盘评估 | **从已收到的询盘开始**，提取主体、需求、市场、数量、目标价格、交期、贸易条件，指出真实性/信用仍需核实项 | 需求简报、客户与项目摘要、澄清问题、英文回复草稿 | 不宣称自动获客或已完成客户尽调 |
| 二、产品需求确认 | 根据客户成熟度走 OEM/ODM/新款路径；按需分析竞品、形成设计简报、AI 模拟图；建立规格与可核价 BOM 关联 | 竞品比较、设计提案、概念图、规格书、结构化 BOM | 概念图不证明精确尺寸、材料性能、工艺或制造可行性 |
| 三、成本核算与报价 | 读取并校验材料/工费/包装等明细、计算适用成本和建议售价、形成报价及排除项 | BOM/成本工作簿、客户报价、方案对比 | 无价格依据不编造；竞品零售价不当作自家成本 |
| 四、打样与确认 | 根据规格形成样品申请/修改指令，整理样品编号、费用、时间、客户意见及批准证据 | 打样指令、样品费用说明、样品反馈/确认记录 | 制作数字材料不等于工厂做出实物；概念图认可不等于样品批准 |
| 五、订单与合同确认 | 对照客户 PO、相应报价和规格，识别冲突，生成 PI 候选和执行前提清单 | PO 差异报告、PI 草稿、需要进一步确认的商务事项 | PI 生成不等于合同已签、定金已到或已批准量产 |

前五个 SOP 是**业务覆盖范围**，不是用户必须依次点击的五个强制页面。打样、核价、议价和订单资料可能交叉进行，产品必须根据真实证据决定可做什么。

## 3. 总体业务顺序与两条工作流的衔接

### 3.1 正常业务主线（允许条件分支）

```text
客户询盘 / 已有产品或订单资料
             ↓
理解需求、识别产品开发类型与未知条件
             ↓
     ┌───────┼─────────┐
     ↓       ↓         ↓
完整OEM资料  现有ODM改款  新款共同开发
规格和BOM复核  基础款+差异   按需竞品研究/设计/生图
     └───────┼─────────┘
             ↓
  对齐当前「可核价规格基线」
             ↓
  BOM/价格/工艺与成本范围核对
             ↓
 不满足目标价或可制造性 → 返回调整设计/规格并重核价
             ↓
 初步报价、客户方案、打样准备资料   [W1]
             ↓
客户议价 / 样品反馈 / 客户要求PI或提交PO  [任一种可先到]
             ↓
根据相应事实完成议价、样品修订、PO核对及PI准备 [W2]
             ↓
正式执行生产需另行满足样品、规格、合同与付款条件
```

早期可以根据基础款或历史数据估计目标成本，辅助设计取舍；但这只是**估价假设**。需要在实际产品方案与 BOM/工艺成本适用后，才可生成对应依据级别的报价。

### 3.2 为什么不能固定「报价→样品→PO」或「样品→报价→PO」

已成熟的 OEM 产品可能先核价后报价，客户同意后才做产前样；新款开发可能先做初样、修改再最终核价；客户也可能要求开 PI 以安排定金后再做产前样。系统保留实际业务事件及其顺序，不以单一固定门禁替代交易双方约定。

### 3.3 两个相关而不依附的工作流

- **W1：从需求到产品与初步商务方案。** 输出可讨论、可核价、有明确前提的产品/价格方案，不宣称客户已接受。
- **W2：围绕已有方案处理协商、样品反馈和订单文件。** 允许从「议价」「样品反馈」「PO/PI」任一事件启动；可回到 W1 补做设计或核价。
- **横向 Change Propagation：**两条工作流和编辑器共用的一套变更机制，不作为客户必须选择的第三个工作流。

## 4. W1：询盘评估 → 产品方案 → BOM 与成本核验 → 报价和打样准备

### 4.1 用户目标与输入

**业务目标：**把询盘及现有材料转成客户可讨论、工厂可继续核价/打样的产品方案和商业材料。W1 不要求每单都同时输出竞品分析、AI 图、完整 BOM 和正式报价。

可选输入包括客户原始询盘/产品图片、现有产品或历史款资料、完整 Tech Pack、用户自有/供应商 BOM 图片或 XLSX、竞品资料快照、LOGO 资源、已核实成本/价格规则及商务条款。原始来源保存并记录版本；没有的资料保持未知。

### 4.2 进入时先判断产品开发路径

| 类型 | 输入成熟度 | 首要工作 | 不应强制 |
| --- | --- | --- | --- |
| A：OEM 来图/来样 | 已有规格、图纸、样品，可能带 BOM | 校验规格/工艺/报价范围，检查缺项，进入核价 | 竞品研究、重新设计、生图 |
| B：现款 ODM 改造 | 指定基础款，要求改 LOGO、颜色、隔层、包装等 | 固定基础款版本，列改动，检查新设计与 BOM 适用性 | 无条件沿用原成本或样品批准 |
| C：新款共同开发 | 只有构想、目标价、参考图片 | 需求澄清，按需竞品分析、设计简报、模拟图；再形成规格候选 | 在设计未定时给出核定成本 |
| D：仅探索可行性 | 初步要求、预算、数量范围 | 给出明确假设的目标成本/可行性讨论和缺项 | 把推测当正式工厂报价 |

路径选择不等于独立四套 Agent。客户追加资料后可以从 C 转 A 的资料成熟度，不必重建 Case。

### 4.3 正常执行步骤

**W1-1：识别客户要求与项目约束。** 提取产品类型、用途、目标市场、数量、目标价、时间要求、颜色/尺寸/材料/结构/LOGO/包装、认证或测试声明、付款与贸易条款。区分客户明确要求、系统建议、商家已知事实与未知项。对缺少的关键条件生成可编辑澄清问题/邮件草稿。

**W1-2：条件性设计研究与美工。** 仅在新款、改款或用户明确要求时分析竞品/历史产品，生成有来源的观察和设计简报；用户选择或修订方案。需要视觉沟通时真实调用图像引擎，生成概念模拟图，形成客户提案。成熟 OEM 资料可直接跳过。

**W1-3：形成可核价的规格基线。** 记录尺寸、结构、面料、里布、填充、拉链/扣具、工艺、LOGO、包装和适用范围；区分缺失参数、推测参数及已确认参数。该基线只需满足当前核价用途，不假装已经具备量产放行条件。

**W1-4：关联 BOM、工艺与成本依据。** 有 BOM 时读取/识别、逐行核对并绑定规格版本；无 BOM 时可整理候选 BOM、询价清单及缺失项。核对材料用量、损耗、工费、包装、检验、运杂与出口相关费用的包含/排除范围，并由确定性计算器算价。

**W1-5：成本反馈设计。** 若目标价、MOQ、工艺或材料可得性不满足，给出可比较的调整建议；用户采纳新的候选规格后，触发横向联动，再核价。成本变化不能自行把用户已有设计要求改掉。

**W1-6：生成本次应交付成果。** 根据输入成熟度输出需求简报、设计提案/图、规格书、BOM/成本工作簿、估价或条件性报价/正式报价草稿、打样要求与样品费用说明。可编辑并按目标受众导出，不允许在客户包中泄露内部成本。

### 4.4 W1 可能的产出、成熟度与完成判据

| 成果 | 在什么情况下生成 | 所需状态/条件 |
| --- | --- | --- |
| 询盘需求与澄清问题 | 所有新询盘或本次要求澄清 | 已知字段有原始来源；关键未知具体可见 |
| 竞品比较、设计简报 | 改款/新款探索或用户主动要求 | 比较有来源、建议未擅自代替客户要求 |
| AI 概念图与客户方案 | 用户需要视觉沟通时 | 标明概念性；图像与当前设计版本对应 |
| 规格书与 BOM/询价清单 | 能形成产品身份和可核价范围时 | 规格基线及 BOM 适用关系明确；未知项列明 |
| 成本与初步报价 | 有足够材料/价格/费用依据时 | 可复算，明确是估价/条件性/可审核报价 |
| 打样资料 | 准备开发样、确认样或产前样时 | 使用的规格版本、样品数量、费用及未确认项清楚 |

**W1 的完成定义依用户当前目标而定。** 例如仅要求设计提案时，完成图文提案不应被判为“BOM 核价失败”；若明确要求正式报价但缺关键成本，应交付已完成部分并显示“待补价格”，不能编造正式报价。

## 5. W2：商务协商、打样反馈与订单/PI 文件准备

### 5.1 用户目标与三个独立入口

**业务目标：**推进 W1 方案的商务接受与实物样品/规格确认；在有 PO 或 PI 要求时核对商务依据，准备对应订单资料。

| 事件入口 | 触发示例 | Agent 应做 | 禁止推断 |
| --- | --- | --- | --- |
| E1：议价/商业回复 | “能不能便宜 5%”“我们同意报价 V2” | 找到明确指向的报价、数量和条款；处理候选议价、判断接受证据、必要时重算 | 询问不等于接受；系统建议售价不等于客户批准 |
| E2：样品反馈/批准 | “样品 S1 的 LOGO 请改小一点” | 绑定实物样品编号、规格版本、意见/照片，形成修改指令与批准条件 | 概念图满意不等于实物样批准；条件性反馈不等于无条件放行 |
| E3：客户 PO / 要求 PI | “这是 PO，请核对并准备 PI” | 读取 PO，核对客户有证据接受的报价与规格；显示冲突、准备 PI 草稿 | PO 到达不等于条款完整；PI 生成不等于签约/收款/开工 |

**E1/E2/E3 不要求按固定顺序出现，也不要求同时出现。** 用户直接上传 PO 可以进入 E3；无需为了跑完整流程先模拟一封不存在的样品批准邮件。

### 5.2 正常业务活动

**W2-1：商务协商与接受记录。** 接收客户议价、调整数量、付款、交期或正式接受。保留客户要求与内部建议的区别；金额、适用数量区间和价格政策重新由程序校验；明确报价内部批准、实际对客报出、客户接受分别有何证据。修订报价形成新工作稿，不覆盖已发报价。

**W2-2：样品制作准备、反馈和版本确认。** 根据 W1 规格生成打样要求，说明样品费用、快递费、预计用时、样品编号与用途。实物制作、发货、签收、测试属于外部现实操作，只能录入实际证据。收到反馈后对照样品/规格版本形成修改清单；对明确、部分、条件性或拒绝批准分别记录。变更规格时重新判断 BOM、报价及已有样品批准适用性。

**W2-3：PO 的业务差异核对。** PO 应优先与**客户有证据接受的具体商业条款**核对，包括买卖双方、款号、规格版、行项目、数量、单价、金额、币种、付款、交期与地点、贸易术语、包装、质量/文件要求。尚无明确接受证据时，将 PO 与已发报价/商家候选作**待协商依据比较**，不能虚构客户已接受的版本。保留原始 PO，不内部改写买方文件。

**W2-4：制作 PI 与订单确认资料。** 基于有依据且正确标注确认状态的条款制作 PI 草稿，必要时附差异和待确认清单；报价、PO 和 PI 的数量/价格/币种/范围需一致或明确展示尚未处理的差异。可在尚待实物样品批准时准备 PI 草稿，但不得把它宣称为生产放行文件。

**W2-5：执行前提说明。** 展示样品/规格批准、双方订单/合同接受、定金或付款保障、必要测试和包装确认等真实状态。工作台不真实收款、不签约、不下生产单。

### 5.3 W2 的分支输出与完成条件

| 本轮目标 | 输出成果 | 可称为本轮完成的条件 |
| --- | --- | --- |
| 处理客户议价 | 新条件比较、修订报价、回复草稿、待批准/待客户确认 | 数字可复算、依据明确、未接受条件仍待确认 |
| 整理样品反馈 | 样品版本记录、修改清单、打样指令、条件性批准记录 | 对应具体样品和规格版本，不夸大批准范围 |
| 核对 PO | 字段差异与来源定位、待确认问题 | 关键差异已核查/分类；有冲突可完成“核对任务”但不能称 PI 已确认 |
| 准备 PI | 有版本和状态的 PI 草稿、客户确认/合同执行前提 | PI 内容与可引用条款一致；硬错误限制对应正式交付用途 |

**W2 与 W1 可往返：**客户要增加电脑隔层可能先触发 W2 的反馈，系统随即回到设计/规格、BOM、成本相关工具；不用重新建询盘，也不必强行重做未受影响的结果。

## 8. 简易 BOM 识别、成本核算与报价

### 8.1 输入与来源

支持**清晰 PNG/JPEG 简易 BOM 图片**和**简单 XLSX 工作表**。读取或 VLM 识别后保留原文件、表格位置、原始值与候选识别值，允许用户逐项核对/纠正。合成测试 BOM 与模拟商家成本表应明确标识，系统需实际读取上传数据，不可由文件名命中预置总成本。

不承诺严重模糊/手写清单、复杂多页组合、宏或所有 Excel 函数都能正确导入。

### 8.2 最小识别字段与业务核对

| 粒度 | 必须提取或核对 |
| --- | --- |
| BOM 行 | 材料/费用项名称、规格、每包用量、单位、单价、币种、原表行小计、原表位置 |
| BOM 表 | 款号/对应规格版本、适用数量/MOQ、原表合计、包含的工费/包装/损耗/检验/运杂等范围及来源版本 |
| 单位和损耗 | 净用量与含损耗计价用量区分，单位换算清楚，重复费用要检查 |
| 未知及核实状态 | 识别不清晰、价格未得到供应商核实、数量区间不适用等分开记录 |

**BOM 识别与核价是两个步骤。** 识别“这张图片写着单价 3.50”不等于 3.50 已被供应商确认；客户效果图也不证明材料清单正确。缺少 BOM 可生成候选清单或询价草稿，但未核实用量与单价不可冒充核定成本。

### 8.3 确定性计算与价格成熟度

```text
行成本 = 每包计费用量（含适用损耗） × 对应单位价格
单位总成本 = 材料行成本合计 + 工费 + 包装/检验/运杂等明确计入费用
建议报价单价 = 计价范围内的单位成本 / (1 - 目标毛利率)
订单货款合计 = 实际报价单价 × 客户订单数量
定金 / 尾款 = 有依据的合同金额 × 已约定比例
```

采用明确的币种、四舍五入/进位规则和费用范围。未披露的费用保持未知，不得视为零；额外费用不重复计算。目标毛利报价是**建议值**，不等于用户已批准对外价格，且与 FOB/FCA 等贸易术语相关的计价包含项要一致。不同报价数量应重新检查 MOQ、价阶、供应能力和费用分摊。模型不直接生成最终金额，由确定性计算器处理。

| 价格状态 | 允许表达 | 不得宣称 |
| --- | --- | --- |
| 目标成本/概算 | 基于历史款或假设的成本区间、开发方向 | 已向工厂确认的正式报价 |
| 条件性报价 | 有明确数据但部分费用、期限、产能或规格待确定的候选价格 | 所有条件均已锁定 |
| 可审核正式报价草稿 | 关键价格、适用规格、数量、贸易条款与费用范围均可复算，可供有权人员审核 | 未经批准即已对客报价或被客户接受 |

### 8.4 成本、售价与版本的关系

- BOM 用量、损耗、原料单价或包装工艺变化：复算成本、候选售价、订单金额；检查相关报价、打样成本和 PI 是否受影响。
- 客户要求折扣或用户直接修改售价：这是**商务售价变化**，不能反向篡改供应商价格或 BOM 来凑数；需显示利润变化及是否仍满足内部规则。
- 成本超出目标或设计超出既有 BOM 适用范围：标记需重新核价，必要时返回设计方案修改；不能拿旧成本冒充新方案的核定成本。
- 已向客户报出、客户已接受或人工锁定的售价：历史/批准状态保留，新价格只能形成候选及影响提示，不得自动覆写原承诺。

### 9.2 编辑本身触发业务变更

编辑文档/表格 → 工作稿保存或稳定提交

→ 识别依赖并标注受影响成果
→ 自动重算/修订/需要时重生图
→ 校验 → 更新工作版本和相关导出件

不要求用户在修改数字后再去 Agent 对话重复说“同步所有文件”，也不应每按一个键就重新生图。无法可靠映射到业务字段的自由文本或复杂表格修改可先保存草稿，但必须标示“需要复核”，旧校验不能继续生效。

人工备注、锁定内容及不相关编辑不能被 Agent 无声覆盖；发生冲突需显示位置与差异。对公式不支持、字段被删除、引用断链或源文件超出兼容范围，保留已编辑劳动，同时阻止使用失效的旧计算证据生成正式业务文件。

### 9.3 受众、成果和原生导出格式

| 业务成果 | 工作台编辑形式 | 导出格式 | 主要受众 |
| --- | --- | --- | --- |
| BOM、成本工作簿 | 工作簿编辑器（已支持公式与业务字段） | **真实 XLSX** | 内部 |
| 设计提案、规格书、打样资料 | 文档编辑器（支持表格与图片） | **真实 DOCX**；客户提案可同时 **PDF** | 客户/供应商 |
| 客户报价 | 受控报价模板/编辑器 | **XLSX + PDF** | 客户 |
| PO 差异与 PI | 文档/结构化编辑器 | **PI：DOCX + PDF**；差异可作为工作台结果或文档 | 内部/客户 |
| AI 产品概念图 | 图片预览、替换和引用 | **PNG/JPEG** | 外观沟通 |

原生 XLSX/DOCX 是可以正常打开/编辑的真实文件，不能用 HTML 改扩展名或截图代替。PDF 和对应可编辑内容使用相同受控内容版本；不在渲染时重新发明另一套金额。

### 9.4 导出件属于联动范围

上游业务字段或图片引用变化后，相关 DOCX/XLSX/PDF 导出副本立即标记为**旧版本/需重生成**；系统自动推进当前工作稿的相关导出刷新，不等待用户手动逐个操作。

- 新格式尚未生成、生成失败、校验未通过、尚需审批时，“下载当前可交付版本”必须呈现正确状态，不能悄悄返回旧文件。
- 历史文件仍可从有明确版本标识的历史入口查看和下载。
- 工作稿保存、业务校验成功、生成文件成功、对外获准交付、实际发出是**不同状态**。
- 某个格式失败应单独报告，不允许用其他格式悄悄顶替，也不能把部分可下载说成完整交付包。

### 9.5 对客信息披露边界

客户报价要从**允许对外字段**生成干净文件，不是仅将内部成本列隐藏。导出校验应覆盖内部成本、毛利、非公开供应商信息、隐藏工作表、秘密公式引用、批注、修订/元数据和未经授权附件。内部草稿即使允许保存，也不能绕过对外交付检查。

## 10. 核心底层能力：变更意图驱动的全链路自动联动

### 10.1 定义与触发

**在工作台识别明确的变更意图或已保存的业务字段变化后，Agent 主动查找本 Case 内全部需要跟随修改的已纳管相关成果（包括间接依赖），自动执行证据充分、可逆的工作稿修订、重新计算、图像更新、校验及 Office 导出刷新；有争议或需要批准的事项交给用户。**

这不是只提醒“文件可能过期”，也不要求用户逐份指示该改哪张表。

| 触发渠道 | 实例 | 判断规则 |
| --- | --- | --- |
| 客户反馈 | 改数量、颜色、LOGO、材料、包装、交期 | 形成客户**请求**，不自动推断双方批准或工厂可执行 |
| 用户主动要求 | “换成彩盒，更新所有关联文件” | 明确变更可以直接查找影响并推进工作草稿 |
| 通用编辑器 | 改 BOM 用量、成本单价、规格参数、客户报价条件 | 保存稳定后识别实际业务字段变化；不要求再次发口头指令 |
| 新上传资料 | 新 BOM、新供应报价、客户更正 PO、实物样品意见 | 对照原依据判断身份、权威与适用范围，不默认“最新即正确” |
| 设计/美工变化 | 改结构、口袋、LOGO、颜色、替换方案图 | 判断图、规格、BOM 和打样资料是否确实受影响 |

用户问“**如果**包装换成彩盒，会怎样？”属于假设/方案比较，不能覆盖当前有效选项；否定、询问、条件性表达均不得误判为已经批准的新变更。

### 10.2 自动处理闭环

```text
客户/用户/文件中的业务事件
             ↓
区分：询问／假设／明确变更请求／实际编辑／确认与批准
             ↓
记录原值、新值、来源、对象、适用版本及影响范围
             ↓
立即将可能过期的当前成果标为“更新中 / 待复核”
             ↓
同时查找直接与间接受影响的工作文件、图像、业务字段和导出件
             ↓
分类：有依据可自动修订｜缺价格/证据｜涉及商业批准｜实际无影响
             ↓
自动更新工作稿、程序复算、需要时重生图、刷新文档引用和导出缓存
             ↓
校验后生成新一致性版本；展示差异、完成项、未完成项和责任边界
```

缺一项供应商价格不代表停止所有工作：可以先更新规格、准备询价问题，阻止的是**对应的新核定报价**；补充真实价格后继续同一变更，不要求用户重建 Case 或从零执行整条流程。

### 10.3 哪些文件在“全链路”范围内

只覆盖**当前 Case 内已上传、系统可读取/已生成、已明确关联、处于支持格式范围的**来源、工作副本、概念图、业务成果与导出版本，包含直接和间接依赖。系统应检查文本引用、表格值、图片引用和不同格式副本，而不只查数据库里的一个总价字段。

对于尚未纳管、无法读取或关联关系不能确定的资料，必须显示“**关联/影响覆盖不完整**”，不得宣称已同步所有真实世界文件。未接入的邮箱、聊天工具或用户本机目录不在实时监听范围。外部已下载/已发送的文件不可自动改写，只能标记需要换发。

### 10.4 典型变更的联动规则

| 变化类型 | 重点影响 | 自动允许的动作 | 不能自动做的事 |
| --- | --- | --- | --- |
| 订单数量改变 | MOQ/价阶、报价、PI、付款计算、订单数量引用与导出 | 检查区间并复算工作稿，刷新相关数字 | 不修改客户原 PO、不无依据改变样品数量、不假定客户接受新数量 |
| 材料/结构/工艺改变 | 规格、设计与图的适用性、BOM、成本、报价、打样、PI | 更新规格候选，查物料/价格适用、按需重新生图 | 不凭图猜用量和供应报价、不自动复用旧样品批准 |
| BOM 用量/单价改变 | 成本、利润、建议售价、报价、必要的 PI | 计算并修订未锁定草稿 | 不覆盖已接受售价、不能反向修改原供应报价 |
| 包装改变 | 包装规格、BOM、设计图相关部分、报价、样品和订单条件 | 已有新成本时复算，更新文字及可见设计 | 没有包装核价/交期依据不能给确定价格/时间 |
| LOGO 位置/颜色改变 | 简报、概念图、规格、打样与工艺成本适用性 | 更新候选规格，按需生图、刷新提案引用 | 不假设视觉变化完全不影响工艺或成本 |
| 仅背景/版式/措辞改变 | 对应图文、相关导出 | 更新表达层并检查是否改变语义 | 不无缘无故重算 BOM 或撤销样品批准 |
| 议价或用户直接改售价 | 报价、毛利、客户回复及 PI 候选 | 重新算利润与条件、修订未发布稿 | 不篡改供应商成本或已对外承诺 |
| 客户更正 PO 错误金额 | PO 差异、PI、必要的报价/金额引用 | 保留新来源，核对并生成正确候选 PI | 不覆盖原 PO；不将内部正确计算冒充客户更正确认 |

“全链路”意为**所有真正相关的成果**，不是每个变更都重做全部文件。可确定不受影响的 Artifact 保持原版本。

### 10.5 自动修改与审批分离

- **工作稿同步默认自动；客户/供应商/内部商业批准从不因同步而自动出现。**
- 已批准、实际对外报价、样品已批准、签署或交付的版本均不可原地覆盖；只能生成候选替代版本并显示需要谁重新确认。
- 人工锁定字段、已编辑备注、已有批准仅在其适用范围内保留。无法安全合并则显示冲突，不能先写后悄悄擦掉。
- 直接改客户售价 ≠ 修改真实成本；客户请求变更 ≠ 客户接受新报价；生成新 PI ≠ 已签署或付款保障已到账。

### 10.6 同步状态与用户反馈

变更一旦被识别，旧版本相关的“已校验/可对外交付”标记立即失效或进入待核实状态，**不需要等待所有图和文档生成完成才提醒用户**。

| 状态 | 含义 | 用户可以做什么 |
| --- | --- | --- |
| **更新中** | 已识别影响，相关工作稿/图片/导出件正在重算或生成 | 查看原工作版本、进度及影响范围 |
| **待补充/待复核** | 缺价格、来源、批准、存在冲突或关联不完整 | 查看缺项、补证、纠正关联或确认候选 |
| **已同步** | 本次相关工作稿与本轮已知事实一致 | 继续编辑、按用途提交审批/生成交付 |
| **更新失败** | 部分步骤失败、结果不完整 | 查看失败点并重试必要步骤 |
| **历史/已替代** | 旧版供追溯；不能冒充当前有效结果 | 查看历史引用与原交付记录 |

同步状态与批准状态并列显示，可同时出现「已同步｜待客户确认」。用户应能查看本轮变化、来源、受影响成果、已经修订/未修订原因、差异和下一步。无歧义草稿修改默认无需逐份点击接受，但仍应允许用户纠正识别、撤销草稿修改。

### 10.7 并发、连续变化和部分失败

- 修改进行中收到第二次变更：旧输入产生的迟到模型、图像、计算或导出结果不得覆盖新的当前版本，需按新基线判断适用性。
- Agent 自己触发的多文档修订属于**同一变更运行**，不能再次递归触发无限同步循环。
- 无关人工编辑尽量保留；与同一字段/同一文件冲突时显示具体冲突，不能无声合并。
- 一份导出生成失败可以保留其他正确成果，但相关交付包不能称为“全部已同步”；恢复后只重试必要分支。
- 原已下载/已对外送达副本只能记录「需要换发」，不能声称远端文件已被系统刷新。

## 11. 知识关联、来源、版本和成果之间的关系

### 11.1 原始资料、Wiki 知识和业务事实必须分层

| 层 | 资料内容 | 在 EasyWork 中的角色 |
| --- | --- | --- |
| **原始 Source** | 客户邮件原文、PO、BOM 图/XLSX、供应商报价、产品/竞品来源及原始附件 | 保留不可改写证据、时间和定位，不由 AI 生成文本代替 |
| **Wiki 知识关联** | 材料/工艺介绍、行业规则、产品知识、竞品特征、SOP、历史经验及交叉链接 | 帮助检索、理解与提出设计/变更影响候选；不能自动证明订单事实 |
| **受控 Case 事实与依赖** | 本订单的规格、BOM 核价范围、报价、客户接受、样品确认、PO/PI 引用与批准记录 | 决定实际计算、版本引用、联动更新与审批门禁 |

候选 Wiki 实现可评估 **OpenWiki 或 LLMWiki** 的来源导入、Markdown 页面关联、检索与 MCP 调用能力，**此文不预先宣称已集成，也不要求同时部署两套**。Wiki 出现「某材料可能影响印花工艺」可作为关联候选；只有 Case 实际采用该工艺且有对应依赖，才据此更新相应业务成果。

### 11.2 来源、工作稿、一致版本、批准、导出五类对象

| 对象 | 定义 | 主要规则 |
| --- | --- | --- |
| Source | 未改写的用户/客户/供应商/竞品原始材料 | 有出处、时间、原始内容和适用范围；新到不自动高于旧来源 |
| Working Draft | 用户/Agent 当前编辑的成果 | 可保存不完整内容；保存不等于验证通过 |
| Consistent Revision | 本轮经过适用检查的相关事实、成果与计算引用快照 | 跨文档改动应同一业务口径一致，不可混新数量旧价格 |
| Approval / Acceptance | 对**具体规格、样品、报价或交易条款版本**的批准/接受证据 | 不因新草稿自动继承或改变对象 |
| Export Artifact | DOCX/XLSX/PDF/图片等可下载文件及版本 | 必须记录引用内容版本、是否生成成功、受众和当前适用状态 |

同一次跨文件修改，相关业务内容核对通过后才能作为一致的新版本。**无关成果不必被迫升版**；旧版本不可覆盖。页面编辑内容、内部计算和导出文件不能维护三份彼此矛盾的数据。新来源发生冲突时需要保留双方并让用户选择或补证，不能按收到时间直接认定最新即正确。

### 11.3 文件与知识之间的关系

Wiki 可以提供跨文档语义提示，但并非“知道哪些文件必须修改”的唯一依据。实际变更传播以**显式业务字段依赖 + 工件版本引用 + 规则校验**为主，Wiki/LLM 辅助发现可能遗漏的文本、设计或材料关联。识别能力不确定时须明确“影响覆盖待复核”。

## 12. 校验、异常反馈与业务完成定义

### 12.1 必须守住的业务规则

| 检查对象 | 必须行为 |
| --- | --- |
| 需求与设计建议 | 客户原始要求、候选研究建议、已采纳方案各自独立；未经批准不覆盖客户要求 |
| 竞品结论 | 数据有可定位来源/时间；不得从少量快照杜撰市场份额或认证 |
| 概念图、规格与 BOM | 图用于视觉沟通；规格和 BOM 要有版次及适用关系；未知用量不能凭图补造 |
| BOM 识别 | 检查单位、小数点、数量、损耗、原表合计；识别准确与价格获确认分开 |
| 数量、MOQ 和成本范围 | 超出价格/产能/MOQ 适用条件后不能沿用旧报价 |
| 金额与公式 | 行价、总成本、毛利、总额、PI 由程序复算；模型一句“通过”不能推翻确定性错误 |
| 贸易术语和交期 | 说明所用术语版本及指定地点/港口；生产周期与到港承诺分开，不造交期 |
| 测试/认证/性能 | 无实证资料则保持未知，不能宣称完成全面市场准入合规审查 |
| 设计、样品和商业接受 | 概念认可、实物样批准、客户接受价格/条款是不同事件，绑定具体版本 |
| PO/PI 与原文 | 原始客户 PO 不被内部改写；差异含原值、依据、建议和解决状态 |
| 变更联动 | 真正相关的已纳管成果已更新或被明确标记；无提示的旧绿勾/旧文件禁止 |
| 工作稿、批准与历史 | 自动更新只改可逆工作稿；已批准和历史交付不得覆盖 |
| 文档编辑与导出 | 编辑后的受影响校验失效；DOCX/XLSX/PDF 使用同一受控事实；对客包不泄露内部成本 |
| 来源与外部指令安全 | 客户/供应商文件中的文字视为资料，不会自动授权执行宏、越权工具、付款或真实发送 |

### 12.2 异常和阻断必须有明确范围与下一步

| 异常 | 正确反馈及继续方式 |
| --- | --- |
| 竞品资料不足 | 缩小结论、列出缺乏的证据，仍可形成待研究设计简报 |
| 图片生成失败 | 保留已经完成的规格/BOM 工作，图像标失败/可重试；旧图不可冒充新图 |
| BOM 图片或表格无法可靠识别 | 定位行/单元格待人工确认，不能输出核定成本；其他不依赖该值的工作可以继续 |
| 成本/包装报价缺项 | 可以形成询价和设计说明草稿，但不能发布假定的正式新报价 |
| 客户只提出条件性样品认可 | 记录条件，制作修改指令；不标记整体样品已批准 |
| PO 金额或条款冲突 | 展示买方原文、商家依据、计算结果和更正要求；可以产出差异报告但不能伪称双方已确认 |
| 用户编辑破坏公式或映射 | 保存草稿，标注业务字段需复核，旧验证结果失效 |
| 关联范围不确定 | 显示可能遗漏的文件和待检查字段；不宣称全部同步 |
| 某一格式导出失败 | 单独显示失败与重试；其他正确成果保留，但完整包不得标全部完成 |
| 迟到的图/计算结果 | 不得用旧输入版本覆盖较新的修改；标记结果已过期 |

错误只阻止对应的成果提交或对外操作，**不是任何警告都使整个 Case 停止**。用户可在原 Case 补充资料继续处理，未受影响的成果保留其正确版本。

### 12.3 完成的定义（按业务目的判断）

**W1 本轮完成：**用户请求范围内的需求整理、设计/规格（按需）、成本/报价或打样准备成果已形成且经适用的计算与业务检查；尚未知的信息与报价成熟度明确披露。不是客户下单成功。

**W2 本轮完成：**用户请求的议价、样品反馈整理、PO 核对或 PI 草稿已完成且有版本/依据；没有收到的客户接受、实物样品批准、定金或合同签署仍显示未确认。并非必须一次完成 E1/E2/E3 全部三种事件。

**变更联动本轮完成：**所有已识别的、受影响的已纳管成果均显示**已同步、待补充/待复核、更新失败或不受影响**，并保留明确版本与来源；不能留下看似当前有效但已经滞后的成果。

**全局语义：**生成 ≠ 已批准；已同步 ≠ 已接受；导出 ≠ 已发送；PI 草稿 ≠ 已签署；付款条件 ≠ 已到账；提案概念图 ≠ 实物确认样；真实系统外部行为若未发生不得伪装完成。
