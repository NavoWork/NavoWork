## 0. 文档范围、来源与使用方式

### 0.1 本版是什么

本版将原 EasyWork 的可靠工作台机制，与“以实际工作成果为中心的一人全流程外贸执行”方向融合为**一份完整产品定义**。

本文不按开发人数、排期或比赛演示裁剪业务范围，不定义研发分工或实现优先级。技术框架、部署拓扑和开发拆包由后续设计决定，不能反过来替代产品目标。

本文重点是单个主操作者与 Agent 的协同。客户、工厂、货代、财务等仍然是真实业务中的责任主体，但不要求他们全部入驻 EasyWork，也不设计多人实时共同编辑和团队协作平台。

### 0.2 来源与新增设计的边界

| 来源 | 本文使用方式 | 不作出的推断 |
| --- | --- | --- |
| [S1] 用户上传的《EasyWork 出海外贸 AI 工作台 · 完整 PRD》V1.0 | 继承首页、多 Tab、业务隔离、Run、快照、确定性报价、资源版本、草稿复核等机制 | 文档描述的目标功能不等于已经上线；原型能力以其自述为依据，本文未审查代码 |
| [S2] 用户提供的跟单员工作成果调研 | 用于覆盖规格、打样、报价、生产、验货、出运及收款等业务成果 | 调研中的典型工作日是重构案例，不是实地工时观测；不沿用其中市场效果或准确率数字作为本产品证据 |
| [S3] 本次对话确认的产品方向 | 坚持一人工作台、真实交付物、轻量业务上下文、人工控制重要承诺 | 不重新回到 CRM、订单监控或自动信息摄取优先的产品定位 |
| [D] 本版融合设计 | 定义 Job、Artifact、依赖、编辑合同、分项确认与完整流程 | 属于产品方案，不冒充已获一线验证或已实现能力 |

未提供的旧版接口文档、分工文档和验收附件不视为已读；本文重新写明完整产品所需的最低合同，不声称同步修改了那些文件。

### 0.3 规范词义

“必须”表示产品验收约束；“允许”表示可支持而非默认执行；“建议”表示推荐的交互或配置；“待验证”表示尚未得到实际业务验证。

所有演示客户、订单、金额和时长均为合成示例。系统不得把示例、估算、模型建议或用户推测包装成真实供应、批准或履约事实。

## 1. 产品定义、价值与边界

### 1.1 产品定义

EasyWork 帮助外贸业务人员在同一个环境中处理多笔业务。用户可以从原始询盘开始，也可以从已经进行中的订单、待修改规格或待检查单证开始；无需先补齐一套 CRM 记录才能工作。

在一笔业务内，用户可以持续完成：

**需求整理 → 规格与打样 → 询价与核价 → 商务确认 → 生产准备与反馈处理 → 验货与出运文件 → 收款跟进与售后材料。**

每次工作应形成可使用的成果：一张真实可编辑的成本表、一份有依据的规格书、一组待审核生产资料、一份定位到原文的差异报告，或一封可以交付的沟通草稿，而不是只有聊天总结和状态更新。

### 1.2 “一个人”的含义

一个主操作者可以调用多种专业能力，完成过去分散在多个软件中的数字工作。它不表示这个人或 Agent 能替代客户批准、工厂生产、现场验货、银行确认或法定签发。

**一个人操作工作台，不等于一个人拥有所有业务权限，也不等于外部参与方已经履行职责。**

### 1.3 产品价值

| 价值 | 用户能够直接感知的结果 |
| --- | --- |
| 减少资料搬运 | 相同数量、规格、条款有受控来源，不必在多个文件中反复重填 |
| 完成工作而非提供建议 | Agent 调用工具计算、编辑、核查和生成可交付文件 |
| 连续推进 | 下一项工作直接使用上一项已保存或已确认的成果，不重新讲背景 |
| 安全处理变化 | 客户改一处，系统提出受影响成果的联动修订，而不是悄悄覆盖正式版本 |
| 降低审阅负担 | 清楚展示改动、依据、未知项和需要人决定的内容 |
| 保持现有交付习惯 | 支持原生业务文件和现有沟通渠道，不强制所有外部人员使用本产品 |

### 1.4 不以什么作为产品中心

不以客户台账、销售漏斗、订单大屏或全渠道消息聚合为中心；不要求用户维护复杂工作流图；不以开放插件市场、任意终端执行或大量 Agent 角色为卖点。

客户、订单、状态、时间线、风险和知识库都存在，但首先服务于完成当前工作。

### 1.5 产品边界

产品包含完整业务链上的数字材料处理、计算、核对、变更、确认记录与授权交付。产品不自行：

- 判定实物已经生产完成或质量合格；
- 伪造客户、供应商、银行或承运人的确认；
- 替代有权主体签署、签发、申报、付款或作出法律合规结论；
- 对缺少真实连接或证据的外部动作宣称成功。

以上边界与业务能力广度无关，不因产品版本升级而取消。

## 2. 用户、责任与使用场景

### 2.1 主要用户

| 用户类型 | 典型工作 | 需要的结果 |
| --- | --- | --- |
| 小型出口企业业务跟单员 | 接收询盘、核对规格、询价、做报价、处理客户修改 | 连续业务上下文与可审阅成果 |
| 兼任生产和单证事务的全流程跟单员 | 制作生产资料、整理工厂反馈、准备出运文件 | 可复用事实、变更影响与跨文件检查 |
| 外贸小团队经营者 / 独立业务经营者 | 同时处理客户、供应商、报价与交付准备 | 单人能操作多种专业工具，且不失去重要决策控制 |
| 工作空间管理员 | 维护商品、模板、业务规则、连接和权限 | 可校验、发布、撤回及追溯的资源 |

采购、业务、运营、单证等名称首先是能力标签，不要求用户切换岗位身份。外部客户、工厂、验货方等可以通过导入证据或连接渠道参与，而不需要成为系统账号。

### 2.2 两类并存的业务

**标准商品业务**：从已有商品、有效价表及供货信息开始，做规格匹配、数量与价格规则检查。

**定制 OEM/ODM 业务**：从需求、图片、规格、打样和供应商报价开始；产品与成本尚未完全确定，需要逐步形成依据。

两类业务共用工作台、成果、版本和交付机制，但不共用所有定价与供货假设。不能把所有定制产品强行匹配到预先发布的 SKU，也不能把标准商品的报价流程无谓复杂化。

### 2.3 高频任务表达

“把这封询盘整理成可以给工厂询价的资料。”

“根据这两家供应商的报价，做一份可解释的客户报价。”

“客户改了包装，检查并更新相关成果，别动已经发出的版本。”

“这张 PO 和客户最后确认的方案哪里不同？”

“基于已确认规格制作生产资料；缺什么批准直接列出来。”

“按这批实际装箱记录生成单证，并检查与订单的关系。”

“整理这次质量投诉的证据与补货方案，先不要对外承诺。”

这些目标可以通过自然语言、快捷动作、成果编辑或导入新材料触发，不需要先手动创建任务记录。

## 3. 融合决策：保留什么，改变什么

### 3.1 保留原 EasyWork 的核心机制

| 原机制 | 本版决定 |
| --- | --- |
| 首页后进入业务 Tab | 保留，首页仍是多笔工作的总入口 |
| 四种业务处理状态 | 保留，继续与业务阶段、运行状态分开 |
| 一个业务一个独立上下文 | 保留，客户相同也不能串用不同订单事实 |
| 对话 + 结构化结果双栏 | 保留为默认布局，不强制改成三栏 IDE |
| 导航无业务副作用 | 保留，切页不执行、不确认、不产生业务版本 |
| 真实模型 + 确定性工具 | 保留，模型不成为金额、权限和状态的最终裁判 |
| 成功结果原子提交 | 保留，扩大为受影响成果及引用的整体一致性 |
| 不可变历史 + 独立工作草稿 | 保留，不让直接编辑绕过业务校验 |
| 授权资源、版本引用和审计 | 保留，并延伸到业务专属文件与交付包 |
| 模拟与真实模式分离 | 保留，不用模拟结果掩盖真实执行失败 |

### 3.2 必须改变的业务假设

1. **Inquiry 不再限定“还没有成交的询盘”**：它的产品语义扩展为贯穿询盘和订单执行的业务 Case。旧内部标识可兼容，但不得继续限制后续业务。
2. **固定三阶段不再代表整个产品**：“读懂询盘 / 准备方案 / 完成回复”成为询盘报价工作的视图；其他工作有自己的步骤。
3. **结果区不再只是固定四块文字**：升级为可编辑、可校验、可比较、可交付的成果区。
4. **报价不再只有 USD 单 SKU 目录价格**：支持定制核价、多行项目、供应商范围差异和明确的币种口径。
5. **文件输入不再只能当附件保存**：需要理解文本、表格、PDF和图片中的有效内容，并定位来源。
6. **导出不再只有 HTML 材料摘要**：支持业务原生文件、版本化交付包与授权渠道。
7. **本版明确纳入生产、验货、出运与收款相关数字工作**：替代 V1.0 的相应范围排除，但不包含未经授权的现实操作。

### 3.3 对上一轮融合建议的修正

**Job 不必成为用户的强制入口。** 它是系统组织跨多次执行的业务目标，用户可以直接开始工作，系统按需生成。

**引入成果中心，不等于新增庞大独立文件管理系统。** 页面中的结构化成果与导出文件必须来自同一个受控内容模型，不让两套事实各自漂移。

**不能把“最新成功版本”当作“最新批准执行版本”。** 草稿工作可以继续推进，已对外报价或已下发生产的版本仍须单独保护。

**不能靠创建更多 Agent 实现全流程。** 关键是可调用的业务工具、明确的执行边界及持续一致的上下文；能力域不等于微服务或独立人格。

**不能把风险门禁扩展成全局停工。** 缺少包装最终价格，可以阻止正式报价，不应阻止制作询问邮件、规格草稿和影响报告。

## 4. 信息架构与页面设计

### 4.1 一级入口

**工作台、知识 Wiki、资产库、能力目录、设置。**

工作台包含首页和已打开的业务 Tab。版本、工作记录、审批和交付均优先以当前 Case 为范围呈现，不新增一套要求用户日常维护的管理模块。

### 4.2 首页

首页继续保留待办、进行中、待确认、已结束四张状态卡和业务列表，同时突出“继续工作”“需要我决定”“开始新工作”。

| ID | 功能要求 | 可观察行为 |
| --- | --- | --- |
| HOME-01 | 四状态卡按用户可访问范围统计 | 四态互斥；未加载不显示假零；筛选只影响列表，不改变全量统计口径 |
| HOME-02 | 列表支持筛选、搜索、排序、分页 | 默认按最后业务更新时间倒序；浏览和切 Tab 不改变排序 |
| HOME-03 | 显示业务与当前工作 | 包含名称、客户、业务阶段、处理状态、当前工作、等待事项、更新时间 |
| HOME-04 | 下一步提示必须有依据 | 来源于明确目标、执行结果、等待事项或批准条件，不凭空生成“逾期” |
| HOME-05 | 支持继续最近工作与查看待决事项 | 一次点击回到相关成果、来源或确认位置，而非只打开泛聊天 |
| HOME-06 | 空状态与错误状态真实 | 无业务时提供创建指引，无待办时不制造工作量；失败可重试 |
| HOME-07 | 多层状态不混淆 | Case 进行中仍可有等待外部回复的 Job，不能把整笔业务误标为全部阻塞 |

### 4.3 创建业务与打开已有业务

用户可以粘贴文本、上传材料、选择模板或描述目标。新建只要求足够识别业务的名称或目标，以及至少一种有效输入；不再强制“必须先有客户名称和客户原文”。

未知客户可保留待补。系统生成的名称只作显示标签，不当作已识别主体。用户可以从“已有订单的装箱单检查”开始，不必重建全部历史询盘。

| ID | 功能要求 | 可观察行为 |
| --- | --- | --- |
| CASE-01 | 一笔连贯交易对应一个 Case | 可从询盘转为订单执行，保留原上下文；独立复购订单可新建关联 Case |
| CASE-02 | 创建幂等与重复提示 | 重复点击不重复创建；疑似重复只提示，不自动合并 |
| CASE-03 | 业务信息允许逐步补齐 | 未知客户、PO号等明确显示；具体工作需要时再请求补充 |
| CASE-04 | 来源导入需明确归属 | 拖入当前 Tab 默认关联当前业务并可确认；多订单材料需拆分或确认归属 |
| CASE-05 | 关闭与重开有原因记录 | 关闭不等于成交、履约或收款完成；重开保留历史 |
| CASE-06 | 业务汇总由有效材料派生 | 用户不必维护另一套完整订单主表；修改关键汇总须回到事实或成果变更 |

### 4.4 Tab 与业务工作区

保持一个 Case 一个主 Tab。可在其内部同时打开规格、成本、报价等成果标签，不为每份文件创建孤立业务上下文。

桌面默认左侧对话、右侧成果，顶部提供业务身份、当前工作、版本、比较与交付入口；可打开资源抽屉。宽屏可展开资源、成果、Agent 三栏，但不是业务机制要求。

```text
EasyWork / 工作台 / 德国背包项目
处理状态：进行中    阶段：报价与定制确认    当前工作：包装变更

[对话与本次执行]              [成果：规格书 | 成本表 | 报价 | 影响报告]
用户目标、步骤、需要补充什么     真实字段、表格、预览、编辑、来源、差异
输入框与附件                  校验、版本状态、保存状态、审核、导出

[资源抽屉] 原始材料 / 已确认依据 / 历史成果 / 交付记录
```

| ID | 功能要求 | 可观察行为 |
| --- | --- | --- |
| TAB-01 | 同一业务唯一主 Tab | 再次打开只激活；关闭不删除，最后一个关闭返回首页 |
| TAB-02 | 上下文与视图隔离 | 输入、语言、所选版本、资源引用和成果标签均绑定用户、工作空间、Case |
| TAB-03 | 运行不依赖页面 | 切换、关闭和刷新不等于取消，返回后可查看真实进展 |
| TAB-04 | 未发送输入可恢复 | 显示未发送/未保存状态；退出或切换账号不泄露给其他账号 |
| WORK-01 | 结果区以成果为中心 | 不是只有 AI 消息；可查看、编辑、比较、检查与交付 |
| WORK-02 | 导航无业务副作用 | 切阶段、选文件、看关系图不调用模型、不批准、不创建版本 |
| WORK-03 | 关键信息可读 | 金额、冲突、未知项不依赖缩放图；窄屏切换“对话 / 成果” |
| WORK-04 | 选择内容可作为操作上下文 | 选中字段、表格行或文件后说“修改这里”，系统展示明确作用范围 |
| WORK-05 | 当前工作可切换但不强迫建任务 | 用户直接操作即可开始；复杂目标由系统组织为 Job |
| WORK-06 | 关系视图只读派生 | 显示实际来源、成果与依赖，不让用户维护连线或另存一套数据 |

### 4.5 成果审阅与交付界面

审阅界面必须能同时看到：改动前后、依据、关联成果、规则检查、未知项以及需谁确认什么。

交付界面必须能看到：用途、受众、收件人或目标、精确文件版本、正文、附件清单、信息敏感性和本次动作权限。用户在这里批准的是**某个具体版本的某项动作**，不是永久授权所有后续操作。

## 5. 核心业务对象与关系

### 5.1 对象定义

| 对象 | 定义 | 不是什么 |
| --- | --- | --- |
| Workspace | 资源与访问的隔离边界 | 不等于一笔订单 |
| Case | 一笔询盘/订单交易的连续业务上下文 | 不等于一项待办或一个文件 |
| Job | 用户希望完成的业务目标，按需创建 | 不要求用户维护复杂任务树 |
| Run | 一次有起止、工具调用、输出和终态的执行尝试 | 不等于整个目标已完成 |
| Source | 原始材料及其不可变版本 | 来源中的陈述不自动成为事实批准 |
| Fact Assertion | 某来源对某业务字段的断言，含范围和证据 | 不等于全局唯一、永远有效的“真值” |
| Artifact | 一个可持续修订的工作成果身份 | 不等于某个导出文件路径 |
| Working Copy | 用户或 Agent 正在编辑的可保存草稿 | 不是已经检查通过的业务版本 |
| ArtifactVersion | 某成果通过结构和业务检查后保存的不可变内容版本 | 不自动意味着批准、发布或发出 |
| Revision | 一次成功业务提交的一致性快照，引用具体成果和事实版本 | 不是把每份文件强制升一个相同版本号 |
| ChangeSet | 一组相关业务修改及其证据、影响和待确认事项 | 不是客户消息到达即生效 |
| ApprovalRecord | 特定主体对特定范围/版本作出确认的记录 | 不是用户“看过”或模型置信度 |
| ReleaseRecord | 将特定成果/方案标记可用于某指定业务用途的记录 | 不等于已经送达、工厂接受或实施 |
| Delivery / Action | 一次导出或外部操作及可核验执行结果 | 不等于成交或现实完成 |
| Issue / CheckResult | 规则检查产生的问题、作用范围和处理状态 | 不等于全部工作必须停止 |

### 5.2 关系与用户负担

```text
Workspace
└─ Case
   ├─ Sources / 业务断言 / 已确认依据
   ├─ Jobs（按需）
   │  └─ Runs → 候选改动、检查、问题、结果
   ├─ Artifacts
   │  ├─ Working Copies
   │  └─ Immutable Artifact Versions
   ├─ Revisions（事实版本 + 成果版本引用清单）
   ├─ ChangeSets / Approvals / Releases
   └─ Deliveries / Actions / Audit Events
```

这些对象大部分是底层机制。用户主要看到“资料、成果、当前工作、待确认事项、版本与交付”，不要求理解技术术语才能操作。

### 5.3 业务范围标识

一笔 Case 内可以有多款、多行项目、替代方案、生产批次和分批出运。事实、成果和检查必须标明其适用范围，例如：

`case → orderLine → variant → scenario → productionLot / shipment → date / version`

不是每个对象都需要全部层级，但不能只用一个全局 `quantity` 解释所有文件。

**一致性要求是同一业务口径无矛盾，不是所有文件中的数字机械相等。** 订单 3,000 件、首批装箱 1,200 件、余量 1,800 件可以同时正确。

### 5.4 上下文边界

同客户不同 Case 可以引用授权的公共商品模板和价格规则，但不能自动继承上次订单的数量、单价、批准、付款状态或收件信息。复制旧订单必须生成新的待确认草稿，并显示被继承内容的来源及需要重新核实的字段。

## 6. 状态、生命周期与事实语义

### 6.1 Case 处理状态：保留四态

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| `todo` 待办 | 已建立，尚未开始实际工作 | 新建 Case |
| `active` 进行中 | 正在推进至少一项工作 | 明确开始、首次运行被接收、恢复或重开 |
| `waiting` 待确认 | 主操作者明确将当前推进置于等待 | 记录等待对象、事项、下一步；有未阻塞工作时提示是否仍需整体等待 |
| `done` 已结束 | 不再推进本笔业务，受控内容只读 | 用户明确结束并说明原因 |

保留转换：`todo→active`、`active↔waiting`、`todo/active/waiting→done`、`done→active`。不允许有处理记录后随意回到待办。

业务阶段是独立标签，例如询盘、打样、订单确认、生产、出运、售后；可并存或回退，不与四态互相推导。付款已核实、某批已出运、一个 Job 完成均不自动结束 Case。

结束前必须解决正在写入的运行或明确取消；外部动作结果未明时不得借结束隐藏其状态。结束不是删除，重开应记录事件。

### 6.2 Job 状态

| 状态 | 含义 |
| --- | --- |
| `ready` | 目标与作用范围已经保存，尚未执行 |
| `active` | 正在执行或处理修订 |
| `waiting_input` | 缺少具体数据或用户决定 |
| `waiting_review` | 候选成果已备好，等待审核或批准 |
| `waiting_external` | 等待客户、供应商或其他外部证据 |
| `completed` | 满足该 Job 的完成标准 |
| `cancelled` | 用户停止该目标，保留过程与成果 |

Job 的完成标准必须与目标一致。“准备报价草稿”可以在草稿合格后完成；“取得客户确认”不能在生成询问邮件后完成。后续新变更可创建关联 Job，不悄悄把历史完成记录抹去。

### 6.3 Run 状态：继承原机制

`queued → running → succeeded / needs_input / failed / cancelled`

`needs_input` 是本次尝试的终态，不让模型调用持续挂起等待几天。问题和候选材料可以持久化，但未通过本次要求的完整检查时，不更新成功业务快照。

补充信息或审核完成后，启动绑定原 Job、问题和基线的新 Run；重新检查来源与版本是否仍适用。服务故障后只可恢复有可验证检查点且安全的步骤，否则明确失败并支持重试。

如果目标仅是生成合格变更提案，Run 可以成功，而 Job 处于 `waiting_review`。这不表示变更已经生效。

### 6.4 成果的三个独立维度

| 维度 | 示例值 | 原则 |
| --- | --- | --- |
| 内容保存 | 未保存 / 工作草稿 / 不可变版本 | 已保存不代表已批准 |
| 使用资格 | 未检查 / 需补信息 / 待复核 / 可用于指定用途 | 可正式报价不等于可下生产 |
| 发布交付 | 未发布 / 指定用途已发布 / 已导出 / 已发送 / 已被替代 | 发布、导出、发送、对方接受相互独立 |

界面可显示“草稿”“待审核”“已发布”“旧版”等简洁标签，底层不能把以上维度塞进一个状态字段并据此推导现实完成。

检查结论绑定内容哈希、规则版本、事实依赖和用途。内容或相关依据变化后，对新用途的检查资格可能失效；历史检查记录本身不可改写。

### 6.5 断言、确认与模型置信度

每条关键断言至少区分：

- **来源声称了什么**：原文、数值、单位、时间、主体、定位。
- **当前采纳到哪里**：候选、冲突、指定范围已采纳、已撤回或被取代。
- **谁有权确认哪一部分**：客户规格确认、供应商成本确认、内部报价批准等分别保存。
- **提取可信度**：模型或解析器对识别结果的估计，仅用于复核排序，不是批准或事实真实性分数。

客户提出改包装是可以有证据记录的事件，不等于工厂已经确认成本。用户记录客户批准时须保留外部依据和记录人；不能显示成系统核验了客户身份或完成了合同签署。

### 6.6 确认与变化状态

客户方案保留 `requested / proposed / accepted` 的语义，`accepted` 绑定具体版本与范围。规格、成本、价格、样品、交期、生产放行分别确认，不用单个“已确认”覆盖全部。

ChangeSet 使用 `proposed / assessing / awaiting_confirmation / ready / applied / rejected / withdrawn`。`applied` 仅表示工作台中获准的变更已应用，不代表工厂或物流已执行；外部实施需另有证据记录。

### 6.7 风险状态

保留未处理、已阅读、已解决，并允许明确的风险接受记录。已阅读不等于已解决；接受某个未知风险不补出缺失事实，也不免除不可绕过的硬规则。


## 7. 通用工作闭环与关键交互

### 7.1 四种平等入口

| 入口 | 用户动作 | 系统行为 |
| --- | --- | --- |
| 自然语言 | “检查这张 PO，再准备 PI” | 识别目标、范围、所需成果和授权边界 |
| 导入材料 | 上传客户新邮件、工厂报价或验货记录 | 关联业务，解析内容，建议可执行工作；上传本身不批准任何变化 |
| 直接编辑 | 在规格书或成本表修改字段 | 保存工作草稿，形成有来源的修改提案并检查依赖 |
| 快捷能力 | 选择“生成 RFQ”“检查单证” | 预填当前材料与目标，明确缺项后执行 |

系统可自动为复杂目标创建 Job，但不得让用户必须填写任务表、选择 Agent 身份或设计工作流才能开始。

### 7.2 一次工作的完整闭环

1. **确定目标与完成标准**：识别当前要交付什么、给谁用、是草稿还是正式用途。低风险简单任务可直接执行；复杂、多文件或对外动作先展示简短计划。
2. **定位上下文与材料**：仅使用授权且与当前 Case 相关的来源，复用已有确认，不重复询问已经有依据的内容。
3. **解释差异与缺项**：区分能立即执行、需要假设、需要外部信息、需要批准的部分。
4. **执行实际工具**：解析、检索、计算、写入草稿、对比或渲染，显示真实进度与工具结果。
5. **检查成果**：结构、数字、来源、业务口径、版本及承诺分别校验。
6. **供用户审阅**：显示成果、字段差异、问题和批准范围。用户可以直接修正或继续自然语言操作。
7. **保存受控版本**：通过检查的改动在一致性边界内提交，旧版本保持不变。
8. **交付并续办**：按用途导出或授权发送，保存交付记录，提供基于实际结果的下一步。

### 7.3 缺项时不要“全做”或“全不做”

用户要求重新报价，但新包装成本未知时，系统应保存新需求、给出影响范围、制作供应商询问和新规格草稿；报价中缺失成本保持未知，不虚构正式金额。

本轮要求的正式报价未完成，则 Job 不完成。可用的草稿记录为候选材料，或以用户认可的“先完成分析/询问”子目标独立提交。系统不得把目标偷偷从“正式报价”换成“分析”后显示全部成功。

### 7.4 人的直接编辑和 Agent 编辑具有同等约束

直接编辑不是低权限聊天的旁路。用户修改数量、单价、规格、交期等字段后，需要同样的计算、来源和批准检查。

同时，人工编辑不应被 Agent 擅自抹去。可保留用户锁定段落、样式和备注；若这些内容与事实冲突，应指出冲突，不能静默保留错误承诺。

### 7.5 停止、撤销和继续

停止 Run 不删除已保存成果；取消未提交候选修改可以撤销；恢复旧版本应创建明确的恢复事件或新版本，不改写历史。

对于已发出的邮件、已创建的外部记录等不可直接撤销动作，只能执行相应更正、取消申请或补充通知，不能显示为本地回滚成功。

## 8. 七大业务能力域

七大能力域覆盖完整产品，不等于七个独立模块、七个 Agent 人格或严格线性阶段。用户可以从任意有真实材料的环节进入，同一业务也可能并行打样、核价与准备出运。

### 8.1 能力全景

| 能力域 | 典型输入 | 主要成果 | 推进边界 |
| --- | --- | --- | --- |
| 1. 询盘与需求澄清 | 客户原文、已知线索、附件、产品参考 | 需求简报、问题清单、澄清回复 | 不伪造客户身份或需求 |
| 2. 产品规格与打样 | 图片、图纸、规格、样品意见 | Tech Pack、BOM、打样指令、修改和批准记录 | 不把图像推断当材料/实测结果 |
| 3. 采购询价与报价 | 已知规格、价表、供应商报价、成本规则 | RFQ、比价表、成本表、客户报价、双语回复 | 不猜价格，不混用报价范围 |
| 4. 订单与商务确认 | 客户 PO、报价、规格、合同和付款条件 | 差异报告、PI、订单确认材料 | 文件制作不等于客户接受或合同签署 |
| 5. 备料与生产跟单 | 已确认订单、BOM、工厂计划与反馈 | 采购/生产资料、T&A、进度差异、变更通知 | 计划、供应商承诺与实际完成分开 |
| 6. 验货与出口出运 | 检验记录、照片、实际装箱数据、运输资料 | QC 汇总、整改、商业发票、装箱单、补料、差异报告 | 不替代现场验货和正式外部签发 |
| 7. 收款与售后 | 商务付款条件、到账证据、投诉与索赔材料 | 收款核对、催款草稿、索赔包、处理方案、复盘 | 付款通知不等于到账；赔偿不自动获批 |

### 8.2 询盘与需求澄清

**用户目标**：把零散客户信息变成可以继续报价、打样或询问的工作材料。

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| INQ-01 | 保存客户原始要求并结构化提取 | 数量、规格、目的地、价格目标、时间要求、定制与文件要求均保留原文定位 |
| INQ-02 | 区分要求、建议、商家事实与未知项 | 备选方案不能覆盖原始要求；不存在的参数不靠默认值补齐 |
| INQ-03 | 生成分组澄清问题 | 按阻碍当前工作的重要性排序，不反复问已有可信答案的问题 |
| INQ-04 | 制作需求简报与客户回复 | 可编辑、双语可选，未知和条件在两种语言中保持一致 |
| INQ-05 | 整理已提供的客户与项目资料 | 可列出需进一步核实的主体信息，不宣称已完成信用审核 |
| INQ-06 | 接收后续反馈并关联原问题 | 保留问题、答复、来源和被更新字段；简短答复不当作全新询盘 |

**成果完成标准**：已知条件可追溯；关键未知可见；下一步能够基于这份材料实际询价或澄清，而非只有摘要。

主动批量获客、营销投放、全网抓取和通用企业征信不是本能力的内置目标。

### 8.3 产品规格与打样

**用户目标**：将客户意图、参考材料和样品修改转成可供报价或生产准备的受控规格。

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| SPEC-01 | 建立结构化规格书 / Tech Pack | 支持尺寸、材料、颜色、结构、辅料、LOGO、包装、标识及要求；模板可按箱包类型配置 |
| SPEC-02 | 区分文本证据、视觉观察和待确认推断 | 图片可识别可见部位；没有依据的材质等级、尺寸、防水性能等保持未知 |
| SPEC-03 | 形成 BOM 与工艺要求草稿 | 用量、损耗、工艺参数各带依据或显式假设，不能把自动拆解结果当工厂确认 |
| SPEC-04 | 生成样品申请与修改指令 | 标明基准规格版本、样品编号、修改部位、数量、用途和待确认时间 |
| SPEC-05 | 接收样品意见与图片标注 | 可定位到部位、字段和版本；保留历史，不用新图覆盖批准样依据 |
| SPEC-06 | 记录分项及条件性批准 | “看起来不错，但改小 LOGO”只能记录已认可部分和未完成条件 |
| SPEC-07 | 比较规格或样品版本 | 展示尺寸、材料、颜色、LOGO、包装等差异及对成本/交期的影响建议 |
| SPEC-08 | 生成指定用途的规格资料包 | 报价规格、打样规格、生产规格分别标明适用范围，未经确认不得标作量产依据 |

**成果完成标准**：接收者能明确知道使用哪个版本、哪些部分已确定、哪些还需要确认。

### 8.4 采购询价与报价

**用户目标**：用可核实的供应信息和清楚的成本口径形成可解释、可修改的报价方案。

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| SOURCING-01 | 根据规格生成供应商 RFQ | 包含数量、版本、工艺、包装、计价口径、需回复字段和未知项 |
| SOURCING-02 | 导入不同格式供应商回复 | 识别行项目、单位、币种、MOQ、费用包含项、有效期和交期条件，保留定位 |
| SOURCING-03 | 统一比较口径并保留不可比项 | 不以缺失费用为零；不同工艺、付款或交货范围不能直接宣布哪家更便宜 |
| SOURCING-04 | 支持目录价格与定制成本两种模式 | 输出共享报价结构，输入依据与规则分别处理 |
| SOURCING-05 | 制作可编辑成本表与客户报价 | 金额由程序计算，内部成本与客户可见售价严格分开 |
| SOURCING-06 | 比较数量、材料、包装等候选方案 | 解释约束和取舍，方案默认 proposed，不能擅自替代客户要求 |
| SOURCING-07 | 生成双语报价沟通 | 与同一事实和报价版本一致；保留排除项、未知项、有效条件 |
| SOURCING-08 | 支持真实报价迭代 | 新数量、新价格依据或定制条件变化触发重算、复核及必要重新确认 |

**成果完成标准**：报价中的有效数字可复算、关键依据可定位、商业范围可解释、重要条款有明确批准状态。

### 8.5 订单与商务确认

**用户目标**：把已协商内容与客户订单对齐，形成能够继续执行的商务资料。

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| ORDER-01 | 解析客户 PO 及相关订单材料 | 提取主体、行项目、数量、价格、规格版本、交期、付款和交付要求 |
| ORDER-02 | 与被引用方案和规格逐项核对 | 不仅比较文字差异，还区分相同含义、实质冲突和缺失信息 |
| ORDER-03 | 制作 PI 与订单确认材料 | 使用明确批准范围的事实；差异未解决时只形成合适用途的草稿 |
| ORDER-04 | 保存接受方案的证据 | 绑定具体版本、条款、外部主体和记录人，问句或条件性回复不等于整体接受 |
| ORDER-05 | 形成执行基准 | 指定哪些规格、价格、交期、样品和付款前提构成后续执行依据 |
| ORDER-06 | 分项检查进入生产准备的条件 | 可准备非正式资料，但未满足条件不得宣称已下单、已批准开工 |
| ORDER-07 | 处理多行、多款与部分确认 | 某行未确定不污染已确认行；正式交付范围必须清楚，不暗示整单已确认 |

**成果完成标准**：商务文件与其声明引用的依据一致；客户接受、内部批准、文件生成和对外交付是不同事件。

### 8.6 备料与生产跟单

**用户目标**：把确认内容转成可执行的生产资料，并依据真实反馈处理差异和变化。

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| PROD-01 | 生成内部采购与生产资料 | 从指定规格、BOM和订单范围生成，标注数量、版本、要求与尚未关闭事项 |
| PROD-02 | 制作时间与行动计划 T&A | 显示前置关系、时间依据、工作日口径、计划与假设；缺产能数据不假装精确排产 |
| PROD-03 | 整理物料到位与生产反馈 | 记录报告方、时间、数量、单位和证据；工厂声称完成不等于系统核实实物 |
| PROD-04 | 对比计划、承诺与报告实际 | 保留原计划与历史承诺，不用最新日期覆盖延期记录 |
| PROD-05 | 处理材料替换、数量与工艺变化 | 形成 ChangeSet，识别报价、规格、样品和排程影响，按范围重新确认 |
| PROD-06 | 生成异常应对与沟通材料 | 可比较赶工、替代、分批等方案；成本和产能没有依据时明确标作待核实 |
| PROD-07 | 管理生产资料发布与外部接受证据 | 已发布、已送达、工厂已接受、已执行分别记录 |
| PROD-08 | 支持多个生产批次与部分完成 | 进度口径一致，不能把局部批次完成显示为全部订单完成 |

**成果完成标准**：资料明确可供谁用于什么；变更未被批准时不覆盖原执行基准；进度差异有来源而非模型猜测。

本能力不是自建工厂 MES、库存总账或自动产线控制系统。

### 8.7 验货与出口出运

**用户目标**：将真实检验和装箱资料变成整改、出运准备和可核对的业务文件。

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| QC-01 | 依据已确认要求制作检验清单 | 规则和标准版本来自适用业务依据，不由模型自动保证适用性 |
| QC-02 | 汇总检验记录、测量数据与照片 | 区分现场结论、记录值和模型观察；照片不替代实物检验 |
| QC-03 | 生成缺陷汇总与整改要求 | 关联部位、批次、数量、证据、要求及复查结果 |
| QC-04 | 保存复验或让步处理记录 | 需要相应责任主体确认；查看报告不等于质量放行 |
| SHIP-01 | 解析实际装箱记录并制作装箱单 | 数量、箱数、重量、尺寸和体积可复核；不从订单量猜测实际箱规 |
| SHIP-02 | 生成商业发票与运输准备材料 | 以明确的订单/出运范围为准，不混用全单和分批数量 |
| SHIP-03 | 核对运输指示与提单草稿等资料 | 显示来源位置、商业差异和需谁确认；不把 Agent 文件当承运人正式签发文件 |
| SHIP-04 | 记录订舱和运输节点资料 | 显示来源时间、计划/预计/实际属性；未连接实时数据时不能声称实时跟踪 |
| SHIP-05 | 检查出运准备条件并形成资料包 | 规则限定适用范围；准备完成、批准出运和实际出运分开 |
| SHIP-06 | 生成基于已核实信息的出货通知 | 船名航次、运单信息和附件等不足时保持未知，发送需授权 |

**成果完成标准**：单证的范围、口径和关键字段相互一致；真实质量与运输事实由相应证据支持。

### 8.8 收款与售后

**用户目标**：把商务付款条件、到账记录和售后证据转成可执行的核对、沟通与处理材料。

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| AFTER-01 | 形成按合同条件计算的应收记录 | 分开预计应收、到期条件、客户付款通知、已核实到账及差额 |
| AFTER-02 | 整理到账证据与核对结果 | 记录证据和核实主体；客户发付款截图不能自动标为银行已到账 |
| AFTER-03 | 生成付款提醒和差异沟通草稿 | 金额与节点引用有效商务条件；缺条件时不杜撰逾期或违约结论 |
| AFTER-04 | 形成放单条件检查材料 | 仅辅助责任人核对；最终放单、付款和银行操作不由模型自主执行 |
| AFTER-05 | 建立索赔证据包 | 关联订单、批次、规格、照片、历史确认和交付记录，不自动判定责任 |
| AFTER-06 | 比较返工、补货、折让等候选方案 | 计算假设明确，补货/退款承诺需明确批准和授权 |
| AFTER-07 | 保存售后处理与业务复盘 | 区分已建议、已批准、已送达和已履行；未核实成本不包装成实际利润 |
| AFTER-08 | 支持结束业务前检查 | 列明未关闭款项、投诉或承诺，但最终结束理由由用户明确记录 |

**成果完成标准**：用户能够拿材料继续核对或沟通；不得仅凭生成一张表宣布钱已收齐或索赔已解决。

## 10. 工作成果系统：编辑、保存、版本与依赖

### 10.1 成果类型与统一能力

成果包括结构化表单、计算表格、正文文档、比较报告、标注视图和交付包。各类成果具有统一外壳：

**标题、业务范围、用途、状态、当前内容、来源、依赖、版本、校验、批准、编辑、比较和交付。**

常见类型包括需求简报、规格书、BOM、RFQ、供应商比较、成本表、报价、回复、打样指令、PO差异报告、PI、生产指令、T&A、QC/整改、发票、装箱单、索赔包。

不是每种类型都要求制作一个全新编辑器。不同成果可共享结构化表格或文档编辑器，差别体现在业务 Schema、模板和校验规则。

### 10.2 内容与文件的关系

结构化业务内容、公式、来源及模板版本构成受控内容模型；XLSX、DOCX、PDF、HTML等是该内容在特定用途下的渲染结果。

导出文件可以带格式、排版和图像，但业务数值不能在渲染阶段被另外计算成另一份真相。文件和渲染结果均记录内容哈希与模板版本。

不承诺任意第三方 Excel、宏或复杂 Word 模板都能无损回写。无法保留的特性必须在导入/导出前披露，必要时将原文件作为只读来源，并生成新的受控成果。

### 10.3 编辑与保存要求

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| ART-01 | 成果真实可编辑 | 表格字段、正文、备注及授权参数可修改，不是只读截图或聊天里的代码块 |
| ART-02 | 区分业务字段与表达字段 | 金额、数量、规格等修改走事实/计算链；排版、措辞等修改也需检查是否引入错误承诺 |
| ART-03 | 自动保存工作草稿 | 显示保存中、已保存、失败与冲突；失败保留本地内容，不能显示成功 |
| ART-04 | 保存草稿不等于形成合格业务版本 | 错误或不完整草稿可保留，但不能获得正式交付资格 |
| ART-05 | 人工与 Agent 改动可比较 | 支持逐项接受/拒绝；需要作为整体一致的改动必须成组处理 |
| ART-06 | 编辑后使相关复核失效 | 改价格或承诺不能沿用旧检查结果；检查绑定准确内容版本 |
| ART-07 | 同成果并发修改需冲突处理 | 基线/草稿版本不匹配时阻止覆盖，保留本地与候选，供重新合并 |
| ART-08 | 保留人工表达及锁定内容 | Agent 不无声重写已编辑内容；与事实矛盾时必须提示而不是盲目保留 |
| ART-09 | 历史内容只读 | 需要修改时创建新草稿或恢复分支，不能就地改历史 |
| ART-10 | 外部编辑后重新导入 | 识别版本标识及差异，走相同检查；不能把本地新文件直接当作新批准版 |

### 10.4 三种版本不要混为一个编号

**Revision**：Case 的成功业务提交编号，例如 R12。记录该时点引用的事实和成果版本集合。

**ArtifactVersion**：某份具体成果的内容版本，例如报价 V3、规格 V5。未被修改的成果不升版本。

**WorkingCopyVersion**：自动保存草稿的编辑版本，用于防止覆盖，不作为用户“报价第几版”的商业编号。

示例：

```text
R11：规格 V5 + 成本 V2 + 报价 V2 + 回复 V2
R12：规格 V5 + 成本 V3 + 报价 V3 + 回复 V3
```

规格未变，因此保持 V5。R12可以是已检查的报价草稿集合，但客户仍可能只接受报价 V2；不能由 R12 更新自动推导客户已接受 V3。

### 10.5 一致性提交

一次跨文件操作先在候选区生成成果并检查。只有受本次改动影响的业务内容、事实选择、依赖和版本引用一致时，才一起提交到新的 Revision。

不要求把整笔 Case 的所有历史材料重新生成，也不要求为无关成果重新审批。文件渲染可先完成暂存再登记，或在内容提交后生成明确的渲染任务；下载入口只有实际可用时才显示成功。

若部分渲染失败，内容保存与文件下载状态必须分别显示，不能让一半文件被误认为完整交付包。

### 10.6 依赖与影响

每份成果记录使用了哪些事实、来源、其他成果版本、规则及模板，尽可能到关键字段/表格行级别。

依赖类型包括：数值计算、语义引用、规格依据、审批前提、展示附件。不同依赖的变化产生不同后果，例如模板改排版不应自动使客户商务批准失效。

LLM 可以建议潜在依赖；已知规则和被记录的引用用于确定性追踪。对于未解析或未纳管的外部文件，只能标记“影响范围未完全覆盖”，不能宣称全库已经完整同步。

### 10.7 有效版本与历史引用

系统同时呈现当前工作稿、指定用途的最新已发布版本、以及实际曾对外交付的版本。历史版本一直可追溯，但当前再使用时需检查依赖变化、撤回证据和当前用途资格。

新价表发布只产生影响提示，不重写旧报价或自动替换既有承诺。已交付报价如需撤回或改价，必须产生新的业务动作与沟通，而不是从历史页面改一个数字。


## 11. 变更、确认与生效机制

### 11.1 变更的触发

客户新要求、供应商新报价、人工编辑、资源更新、工厂反馈和检查发现的错误都可触发变更提案。系统必须识别它是：

**新增信息、修正提取错误、修改业务要求、替代方案、状态证据更新，还是只改表达/排版。**

不同类型不能使用同一条“覆盖最新值”逻辑。

### 11.2 变更处理要求

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| CHG-01 | 生成字段级变更提案 | 记录旧值、新值、范围、来源、提出方、原因和基准版本 |
| CHG-02 | 分开客户请求和可执行方案 | 客户要求不被系统内部建议替代；新成本、新交期需独立核实 |
| CHG-03 | 展示直接和间接影响 | 列出受影响成果、需重算内容、待重新确认事项及未纳管范围 |
| CHG-04 | 允许先生成候选成果 | 可制作草稿、询问和影响报告，不等于生效 |
| CHG-05 | 对关键变化重新检查批准适用性 | 数量、价格、规格、交期等实质变化只能在相应范围使旧批准不再适用于新版本 |
| CHG-06 | 成组应用依赖修改 | 接受规格变更但拒绝必要成本重算时不得生成自相矛盾的正式报价包 |
| CHG-07 | 支持部分接受与明确待定 | 对独立范围可分别决定；有依赖的部分必须说明联动约束 |
| CHG-08 | 生效前再核对当前基线 | 处理期间若有其他提交，不得把旧提案直接覆盖新状态 |
| CHG-09 | 保留原正式版本与交付记录 | 新版本替代关系可见；旧内容不被删除或改写 |
| CHG-10 | 外部实施另行记录 | 工作台内应用、通知发出、供应商接受和实际执行分别有证据 |

### 11.3 批准不是单个布尔字段

ApprovalRecord 至少包含：

**批准对象及版本、业务范围、批准类型、决定、条件、有效依据、作出决定的主体、代为记录人、记录时间、适用性检查。**

典型类型包括客户规格批准、样品批准、供应商成本确认、内部价格批准、交期承诺确认、生产资料发布、出运放行和对外发送授权。系统按当前业务配置选择必要项，不能对每个小任务都机械要求全部类型。

单人企业可由同一有权限操作者作内部批准，不强制找第二个账号；但这个操作者不能仅靠点击按钮替代客户或供应商的外部确认。记录外部确认需要证据或清楚标记的人工记录来源。

### 11.4 批准后的继续编辑

内容发生实质变化后，必须重新判断批准是否仍覆盖该内容。例如只改排版可保留商业批准，但金额、规格或交期变化必须重审相应范围。

对于内部草稿，“已审核”不是无限期资格；任何人工修改后都要检查适用规则。对于已发出材料，原批准仍作为历史记录保留，新版本需新的适用判断。

### 11.5 生效与执行基准

可按用途形成独立的有效基准，例如：

- 客户当前接受的报价与条件；
- 工厂可用于某批次生产的规格和指令；
- 某次出运的装箱与单证资料；
- 经责任人核实的收款状态。

不使用一个全局 `currentRevision` 代表全部有效执行事实。工作台可以正在做 R15 的新草稿，而工厂仍按 R12 对应的已发布规格生产。

### 11.6 版本冲突与并发变更

两个来自不同来源的相同字段变更不得靠时间戳自动决定谁正确。应展示各自主体、时间、来源及适用范围，并由业务规则或用户补证解决。

若修改来自同一主操作者的多个窗口，系统按基线版本检测冲突。即使不支持多人实时编辑，也必须防止多 Tab、多设备和迟到的 Agent 结果互相覆盖。

## 12. 报价、成本与确定性计算

### 12.1 两种定价路径

| 路径 | 输入 | 必要校验 |
| --- | --- | --- |
| 目录报价 | 已发布商品、数量、有效价阶、已知供货信息 | SKU、MOQ、数量范围、单位、币种、时效及供货条件 |
| 定制核价 | 规格、BOM、供应商报价、工费、包装、费用规则、汇率与定价策略 | 成本覆盖范围、单位、币种、报价有效条件、重复计费及未核实假设 |

定制路径允许基于外部供应商报价和有权限用户录入的业务依据，不要求所有价格事先存在全局商品目录。但每笔重要价格必须能解释从何而来、适用于什么。

### 12.2 报价组成

产品成本、包装、模具/打样等一次性费用、本地或运输费用、税费以及其他条款允许按实际业务模板组合。某项是否适用、是否已包含、如何分摊均需明确。

对未知项使用 `null` 和原因；确实不适用的费用记录“不适用”；已包含的费用记录“包含于哪一项”。三者不得都变成零。

报价应分开：已知金额小计、明确排除项、未知费用、方案商业总额与是否具有完整金额资格。已知商品价不意味着到岸总成本已经确定。

### 12.3 核心计算要求

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| QUOTE-01 | 来源与范围明确 | 每项价格、数量、单位、币种和有效条件可定位 |
| QUOTE-02 | 确定性金额运算 | 使用受控十进制定点策略；最终结算金额按币种规则处理，不能使用不受控浮点造成差异 |
| QUOTE-03 | 单价和分摊保留所需精度 | 单价可有高于最终金额的精度；明确逐行/汇总舍入时机和方式 |
| QUOTE-04 | 多行项目与方案隔离 | 总额来自指定方案、行项目与数量，不能混合备选方案 |
| QUOTE-05 | 多币种比较基准明确 | 汇率值、来源、时间、方向、用途和舍入策略可追溯；无汇率不得伪造统一币种总额 |
| QUOTE-06 | 毛利率和加价率区分 | 定价规则明确分母，不把 cost×(1+rate) 和 cost/(1-rate) 混用 |
| QUOTE-07 | MOQ、供货与价格资格检查 | 已知违反约束的方案不得标为可执行有效报价；建议调整须另建候选 |
| QUOTE-08 | 时间口径拆开 | 生产、付款后出库、运输、到货分别记录，不能从其中一个推出其他确定日期 |
| QUOTE-09 | 费用与条款范围明确 | 贸易条件、地点、适用版本或其他必要条款按业务依据记录，不由模型补政策 |
| QUOTE-10 | 变化重新计算和审校 | 数量、规格、费用、汇率或规则变化都应识别受影响部分 |
| QUOTE-11 | 内外报价视图区分 | 客户报价不自动包含成本、供应商底价、毛利、内部备注与完整原始附件 |
| QUOTE-12 | 内部估算与正式报价隔离 | 估算显示假设和范围，不因用户接受 warning 就变成已核实报价依据 |

### 12.4 供货状态

已知库存不足或明确不满足 MOQ 时，可以形成替代/分批建议，但不允许给原方案贴上“可按量供货”标签。

库存未知可以形成供货待核实的草稿；定制生产不应机械套用现货库存条件，应使用工厂回复、MOQ、产能和相应商业前提。没有实际预留接口与成功结果时，不显示“库存已锁定”。

### 12.5 公式示例，仅用于产品测试

若企业选定“目标毛利率”模式：

```text
报价单价 = 符合范围的单件成本 ÷ (1 − 目标毛利率)
毛利率   = (售价 − 对应成本) ÷ 售价
加价率   = (售价 − 对应成本) ÷ 对应成本
```

上式只是选定规则下的算术，不自动定义哪些成本应包含，也不代表财务报表中的实际净利润。

假设成本 ¥50/件、汇率 7.20 CNY/USD、目标毛利率 20%，按美元单价向上取至美分，得到 $8.69/件。若已核实新包装使成本增加 ¥3/件，相同规则得到 $9.21/件。3,000件的报价商品金额分别为 $26,070.00 和 $27,630.00，差额 $1,560.00。

这些数字是测试假设，不是实际商品价格或完整贸易成本模型。

## 13. 审校、风险与业务门禁

### 13.1 三种检查边界

| 边界 | 检查目的 | 失败结果 |
| --- | --- | --- |
| 工作草稿保存 | 不丢用户劳动，记录未验证内容 | 允许保存但标明错误/缺项，不作为成功业务版本 |
| 业务版本提交 | 确保本次声明完成的成果内部一致、引用真实 | 硬错误阻止该一致性单元提交，上一成功版本不变 |
| 指定用途发布 / 导出 / 发送 | 检查本次受众、用途、确认、敏感信息和权限 | 不满足则阻止该动作，而非禁止一切后续工作 |

“没有某项最终价格”可以阻止正式报价，但不应阻止导出一封明确询问该价格的供应商邮件草稿。两个成果具有不同的完成标准与交付条件。

### 13.2 严重性与作用范围

`error`：会使指定成果或动作实质错误、越权或误导，必须阻止对应提交/交付。

`warning`：可以诚实披露的未知、待核实或有条件限制；只能在适当用途下继续。

`info`：说明或无需阻断的建议。

每项检查必须包含目标范围、规则依据、严重性、证据、修复方式和对哪些动作有影响。不是一个与用途无关的“全系统风险等级”。

### 13.3 业务不变量

| ID | 不变量 | 必须处理 |
| --- | --- | --- |
| BR-01 | 不伪造业务事实 | 缺失价格、尺寸、日期、批准和实际进度保持未知 |
| BR-02 | 金额可复算 | 计算输入、公式口径、精度及规则版本可追溯 |
| BR-03 | 未知不等于零 | 不适用、已包含、未知、真实零值分别表示 |
| BR-04 | 计划、承诺、实际分开 | 不用最新承诺擦除历史计划和延期 |
| BR-05 | 外部声明必须有相应依据 | 认证、库存、交期、付款等不得由生成文本自行证明 |
| BR-06 | 备选不等于接受 | 明确批准对象、范围和外部反馈依据 |
| BR-07 | 客户原始要求不被建议覆盖 | requested、proposed和accepted分别保留 |
| BR-08 | 同口径内容一致 | 同订单行、方案、批次及时间范围无矛盾；合法分批通过显式映射解释 |
| BR-09 | 重要变化需要重新判断批准 | 对新版本重新检查，历史批准记录保留 |
| BR-10 | 引用固定版本且可访问 | 资源更新不静默改历史；引用权限参与使用和交付检查 |
| BR-11 | 阅读或接受风险不等于事实补齐 | 不能借“已知悉”绕过硬规则 |
| BR-12 | 制作、导出、发送、接受、履约分开 | 每类状态由对应事件或证据驱动 |
| BR-13 | 文件同名不等于同版本 | 以内容版本、哈希和业务范围判断 |
| BR-14 | 单据比较考虑业务范围和转换 | 不能把全单/分批、净重/毛重、单位换算机械判成错误 |
| BR-15 | 已发布内容不可原地修改 | 变更生成新版本和明确替代关系 |
| BR-16 | 客户/供应商不得收到未经许可的内部信息 | 检查字段、隐藏页、附件、批注、元数据及引用链接 |
| BR-17 | 外部结果不明不得假装失败或成功 | 进入结果未知与核查流程，禁止盲目重发 |
| BR-18 | 来源可信与操作授权相互独立 | 一封真实客户邮件也不能授权系统付款或变更银行资料 |

### 13.4 双语与文字审校

文字审校需要检查数量、SKU/规格、金额、语言中的条件性和确定性表达，以及客户批准状态；不能只查语法。

两种语言可共享同一业务事实，但独立编辑草稿。修改一个语言不自动无声覆盖另一个；系统提示需同步/复核，并显示具体差异。保留 V1 的中文界面、en-US与es-MX输出基础，其他语言通过明确的已支持语言列表开放。

检查器应与生成过程逻辑分离；确定性规则失败不能由模型一句“检查通过”解除。

### 13.5 规则发布与历史

规则来自企业配置、业务要求或明确适用的外部依据。新规则发布生成新版本，历史报告保留原检查依据；当前重新交付时可能需按适用新规则复查。

对于法规、标准和复杂贸易解释，产品提供依据整理和证据完整性检查，不自行给出无需专业复核的合规保证。

## 14. Agent 执行、运行恢复与能力管理

### 14.1 执行模式

| 模式 | 适用内容 | 控制方式 |
| --- | --- | --- |
| 直接执行低风险工作 | 读取授权材料、计算、生成可逆草稿、检查 | 在当前目标和权限内执行并留痕 |
| 预览后应用 | 多成果修改、改变重要业务字段 | 展示计划/差异，用户确认后提交相应改动 |
| 明确授权外部动作 | 发送、写回外部系统、发布生产资料 | 绑定内容、对象、范围、权限与有效期 |
| 禁止模型自治 | 未经验证付款、银行账户变更、最终实物质量结论等 | 提供辅助材料，由有权主体处理 |

不是每次工具调用都弹确认框。确认应聚焦真正的业务决定和外部副作用，避免把工具操作负担转回给用户。

### 14.2 运行要求

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| AI-01 | 识别目标与完成标准 | 输出本次 requiredOutputs、作用范围和需要授权的动作 |
| AI-02 | 使用真实结构化工具结果 | 不把模型描述当作解析、计算、保存或发送已成功 |
| AI-03 | 展示执行摘要 | 显示读取、计算、生成、检查等真实步骤，不伪造内部思维过程 |
| AI-04 | 执行前检查依赖和预算 | 必需工具不可用则阻止相应运行，可选跳过说明影响 |
| AI-05 | 控制同业务写入 | 同一 Case 的业务提交按序和基线控制；允许只读/候选计算并行但不互相覆盖 |
| AI-06 | 新信息关联原目标 | 补答绑定 Job、Run和问题，不能丢失之前的约束 |
| AI-07 | 幂等、取消与迟到结果保护 | 重复提交不重复产生版本；取消后迟到结果不提交 |
| AI-08 | 运行失败保留有效成果 | 显示可执行的修复建议，不能退化为示例成功 |
| AI-09 | 上下文使用受控 | 当前画布选择、相关来源及有效基准进入上下文；不把全部客户资料无差别发送给模型 |
| AI-10 | 可恢复但不虚构恢复 | 检查点可验证才续办，外部动作先核查结果再决定重试 |
| AI-11 | 支持预定范围内的事件触发 | 仅在用户明确配置的 Case/来源/能力/权限内触发，默认不全域监控 |
| AI-12 | 记录真正未完成事项 | 成果草稿生成成功不掩盖核价、批准、发送或外部执行未完成 |

### 14.3 运行终态判定

| 情况 | Run终态 | 业务效果 |
| --- | --- | --- |
| 无法识别本次目标，或缺本次必需事实 | `needs_input` | 保留输入、问题和候选草稿，不提交不合格业务版本 |
| 用户仅要求分析，已有材料足够 | `succeeded` | 可提交分析成果；无有效报价就不显示报价完成 |
| 用户要求形成待审变更，提案完整且合格 | `succeeded` | 保存提案，Job可转待审核；不改变已发布执行基准 |
| 可以披露的未知不影响指定用途 | `succeeded` | warning随成果保留，用途与限制明确 |
| 输出有未纠正的硬错误或工具故障 | `failed` | 上一成功版本保持，候选内容标为未通过 |
| 用户取消，尚无不可逆动作 | `cancelled` | 不提交迟到结果；已完成部分有真实记录 |
| 外部动作请求后连接中断，无法确认结果 | `needs_input`，原因标为`external_result_unknown` | Action为`outcome_unknown`，Job为`waiting_external`；先核查结果，禁止自动重复执行 |

最后一行必须区分运行控制状态和外部业务结果；界面不能只显示一个含糊的“发送失败”。

### 14.4 能力目录

能力以业务目标展示，如需求理解、规格制作、供应商比价、成本核算、PO核对、生产资料、出运单证、变更检查。

每项能力说明支持输入、实际输出、规则、所需权限、可用状态和限制。配置可以有内置工具、专用业务模块和真实连接器，但产品不要求开放任意插件安装、CLI或MCP执行平台。

能力域可以由一个主控与多种工具完成。底层 Agent 数量或框架不成为用户交互概念，也不作为 PRD 的强制实现方案。

## 15. 交付、连接器与外部操作

### 15.1 三种交付模式

| 模式 | 行为 | 必须显示 |
| --- | --- | --- |
| 导出草稿材料 | 下载供内部核对或带明确待确认项的业务草稿 | 用途、版本、状态、未知项和生成时间 |
| 发布受控文件 | 将已满足条件的成果用于指定正式业务目的 | 使用范围、批准依据、文件清单与有效版本 |
| 授权外部操作 | 通过实际连接发送或写回外部系统 | 目标、内容、附件、授权、执行结果及外部标识 |

系统不允许以“导出草稿”绕过同一用途的硬性错误。与该错误无关的合格澄清材料可以单独交付，但必须具有独立清楚的用途和检查。

### 15.2 原生文件与交付包

支持适用于成果类型的 XLSX、DOCX、PDF、HTML，以及多文件交付包；邮件草稿可复制或导出，接入发送渠道后可授权发送。

业务表格的公式、单位、币种和精度应保留或清楚披露导出限制；文档版式与文件名、版本标识、页眉/页脚等可使用企业模板。内部可完整追溯，外部只披露获准信息。

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| DEL-01 | 指定精确版本与用途 | 不隐式导出另一个最新版本；历史版本导出显式标明历史状态和用途 |
| DEL-02 | 导出前再校验 | 内容、依据、批准、模板和敏感信息检查均绑定本次清单 |
| DEL-03 | 交付包具备清单 | 保存成果版本、语言草稿版本、附件版本、用途、时间和哈希 |
| DEL-04 | 所见、复制、导出一致 | 同语言同版本读取同一草稿或成果，未保存内容不冒充已保存 |
| DEL-05 | 受众视图可靠 | 客户、供应商、内部三种受众按配置过滤敏感内容，不只在界面隐藏 |
| DEL-06 | 输出文件实际可用 | 文件能打开、关键内容不截断、数字正确、页数和格式符合模板声明 |
| DEL-07 | 导出不改变业务事实 | 不自动成交、客户接受、已发送、已下单或已收款 |
| DEL-08 | 外部修改回传可识别 | 与原交付版本比较，必要时重新校验和确认 |

### 15.3 对外信息保护

内部成本、供应商报价、毛利率、内部风险备注、其他客户信息和未授权来源附件默认不得进入客户交付包。

检查必须覆盖实际文件：隐藏工作表、批注、修订记录、公式外链、嵌入对象、文档元数据以及附件名称。外部文件中的“来源”可采用允许披露的依据描述，不强制暴露企业内部全文和链接。

权限控制不是简单按某个文件标了“客户版”就放行；每次最终交付仍需检查清单和实际输出。

### 15.4 真实发送与授权

发送授权绑定收件人、渠道、标题、正文、附件哈希及内容版本。授权之后任何重要内容变化都需重新确认。

单次授权与持续授权分开。持续授权只适用于明确限定的低风险动作、接收对象、模板、有效期和触发条件，不能被模型扩展为任意发送许可。

没有真实渠道或连接失效时，系统降为明确的草稿/导出模式，不能显示真实已发。用户手工在外部发送后，可记录“用户声明已发送”和证据，不能伪造供应商回执。

### 15.5 连接器策略

手动上传/导出是完整产品的一等使用模式，连接器只增强输入与执行，不是开工前提。

连接状态必须分开表示未配置、只读可用、写入可用、过期、权限不足和故障。每个具体动作检查真实连接的能力，不能因显示邮箱或ERP图标就宣称完整接入。

连接器可以提供邮件、企业文件或具体业务系统的读写；产品不承诺对任意平台实现全量双向同步。

### 15.6 外部动作结果

`prepared → awaiting_authorization → queued → executing → succeeded / failed / outcome_unknown / cancelled`

发送成功仅表示连接器返回相应成功证据，不自动表示客户阅读、接受或工厂执行。结果未知时先查询外部回执或请求用户核实，不能盲目重发产生重复承诺。

## 16. 账户、权限、隐私与数据安全

### 16.1 权限基线

继承管理员/成员两种基础角色。岗位是能力标签，不是权限身份。单人空间中同一人可兼任管理员和业务操作人，不因产品流程强制增加协作账号。

内部批准、发布和对外动作可配置独立权限。外部客户或工厂的批准仍依赖相应证据，不因为操作者是管理员就自动成立。

| ID | 功能要求 | 验收与边界 |
| --- | --- | --- |
| AUTH-01 | 真实认证、退出与会话恢复 | 过期停止写入和外部操作，保留未提交输入并提示 |
| AUTH-02 | 工作空间和资源级授权 | Case、Run、版本、草稿、文件、事件流和导出均检查归属 |
| AUTH-03 | 查看权限与操作权限分开 | 能看文件不等于能正式发布、发送或改连接设置 |
| AUTH-04 | 同工作空间访问规则明确 | 延续基础可见范围，敏感资源如需限制应明确；不假定不同账号天然不可见 |
| AUTH-05 | 文件与链接受控 | 下载、预览、历史链接及外发分享都不能绕过权限 |
| AUTH-06 | 权限变化即时影响新操作 | 已撤销用户或凭证不再能发起调用；历史记录按保留政策可审计 |

### 16.2 外部内容与模型边界

客户邮件、PDF、网页及附件中的指令均是待分析内容，不具有系统权限。不得因此读取其他 Case、泄露文件、修改授权或执行未声明操作。

上传文件的脚本、宏或可执行内容不能自动运行。运行环境应限制可读资源、网络目标和工具参数；模型凭证不进入浏览器、导出文件或业务日志。

### 16.3 数据治理

原始文件、派生结构化内容、工作草稿、正式版本、审计记录和模型运行日志分别设置保留策略。用户应能了解哪些数据会发送给何种外部模型/工具，以及当前工作空间的相关设置。

删除、归档、权限撤销和保留期到期是不同动作。需要删除的敏感原件不应因为“历史可追溯”被永久保留；在允许的范围内保留必要事件和版本标识，并明确证据已不可访问。不能以证据被删除后仍伪造其可用性。

具体合规义务、地区部署和模型服务条款由真实企业政策与服务配置决定，本文不假定所有供应商都满足相同要求。

### 16.4 审计要求

记录重要提交、人工校正、确认、发布、授权、外部动作、资源更新、结束重开与删除事件。内容包括操作者、对象版本、作用范围、时间和结果。

日志只保存定位问题所需内容，不无差别打印客户全文、凭证、完整银行信息或全部附件。


## 17. 数据与接口的产品合同

本节定义必须保持一致的产品语义，不指定数据库、框架或微服务架构。字段名为概念合同示例，具体机器可读 Schema 不得改变其含义。

### 17.1 关键对象的最低数据要求

| 对象 | 必须保留的信息 |
| --- | --- |
| Case | workspaceId、业务身份、客户线索、业务阶段、处理状态、当前成功Revision、元数据锁、等待/结束原因 |
| Job | caseId、用户目标、范围、完成标准、requiredOutputs、状态、问题、关联Runs与产物 |
| Run | jobId、caseId、baseRevision、输入引用、模式、能力版本、幂等键、执行事件、终态、错误/待补问题 |
| SourceVersion | 原始内容位置、哈希、类型、归属、来源主体、时间、解析版本、定位索引、敏感性 |
| FactAssertion | 字段路径、原始/规范值、单位/币种、业务范围、来源定位、断言主体、确认记录和适用状态 |
| Artifact | caseId、成果类型、标题、范围、用途、编辑器类型、候选/当前版本引用 |
| WorkingCopy | artifactId、baseArtifactVersion、baseRevision、draftVersion、内容、修改人、保存与检查状态 |
| ArtifactVersion | 不可变内容/哈希、依赖引用、schemaVersion、templateVersion、生成依据、检查记录 |
| Revision | 提交号、事实引用集合、成果版本清单、本次ChangeSet、前一版本、提交人/Run与时间 |
| ApprovalRecord | 对象与版本、类型、范围、决定及条件、外部决策主体、证据、记录人、时间 |
| ReleaseRecord | 发布用途、成果版本清单、批准引用、条件、发布人、时间、替代关系 |
| ChangeSet | 基准、变化明细、影响、待确认、被接受/拒绝项、状态和应用结果 |
| CheckResult | 规则版本、内容/依赖哈希、检查范围、用途、严重性、证据、修复入口 |
| ExportManifest | 用途/受众、准确版本清单、文件哈希、语言、过滤策略、生成状态与时间 |
| Action / Delivery | 外部渠道、目标、内容清单、授权、幂等标识、状态、结果证据和外部引用 |
| AuditEvent | 事件类型、主体、目标、作用范围、发生时间、前后关系与结果 |

### 17.2 关键写入合同

**合同 A：业务版本提交**

输入包括 Case、baseRevision、预期修改范围、候选事实与成果、依赖、检查结果和幂等键。提交方必须重新验证权限、基线、检查适用性及状态。

有业务内容变化的提交成功后，生成一个不可变 Revision，并原子更新本次涉及的当前工作引用。任何冲突、取消或硬错误都不得产生半套成功结果。

只读查询、未保存为新成果的检查、预览、导出，以及没有业务内容变化的运行，可以成功而不新增 Revision。批准、发布、交付和元数据调整使用各自事件记录；只有其引起新的业务内容或事实选择时才另行提交相应业务变更。

**合同 B：人工草稿保存**

输入包括成果、基线内容版本、draftVersion和编辑内容。保存失败或冲突时保留用户内容，返回明确冲突信息，不覆盖服务器已有草稿。

草稿保存不产生新的成功业务Revision，也不延续过期的审核资格。

**合同 C：批准与发布**

批准绑定精确内容与范围。批准、发布和客户/供应商接受不能互相代替。发布前再检查依赖与批准适用性，发布记录不可通过改标题或切阶段生成。

**合同 D：导出与外部动作**

导出/发送使用不可混淆的Manifest。授权绑定该Manifest以及目标。执行前验证内容未变化、权限仍有效；结果必须写回本次Action，而不是仅写一条聊天消息。

**合同 E：资源更新**

资源发布生成新版本，返回实际引用它的工作范围。系统只标注需要关注或复查的依赖，不自动替换历史。

### 17.3 必须区分的版本号

`metadataVersion` 负责 Case 名称等元数据并发；`revision` 负责成功业务提交；`artifactVersion` 负责成果内容；`draftVersion` 负责编辑冲突。

改标题、切 Tab、阅读风险、复制文本或调整语言偏好都不应新增业务 Revision。

### 17.4 事件合同

事件至少包含 workspaceId、caseId、runId或相关对象、事件序号、时间、类型和实际结果。前端只能将事件归入其对应业务，不能让当前激活的 Tab 接收其他 Case 的结果。

典型事件包括运行接收、步骤开始/完成、候选就绪、需要补充、检查失败、提交成功、等待批准、导出就绪、外部动作成功/结果未知。

事件流不是唯一持久化来源；刷新后能够查询权威状态。重连可能重复收到事件，界面应去重。

### 17.5 错误分类

至少区分认证过期、无权限、上下文归属错误、基线冲突、缺少业务事实、业务规则不通过、不支持文件、解析失败、模型/工具超时、导出失败、外部动作结果未知和取消。

每类错误需要可理解的说明、受影响范围以及下一步；不能全都显示“生成失败，请重试”。

## 18. 异常、恢复与非功能要求

### 18.1 核心异常要求

| ID | 场景 | 必须行为 |
| --- | --- | --- |
| NFR-01 | 登录过期或权限撤回 | 停止新写入/动作，保留未提交内容并提示；接口不返回无权资源 |
| NFR-02 | 网络或自动保存失败 | 显示未保存并允许重试，重复请求不重复建业务或版本 |
| NFR-03 | 模型结构输出无效 | 不进入正式版本；可有限修复，超限明确失败 |
| NFR-04 | 文件解析不完整 | 展示已处理/未处理范围，关键缺项不被隐藏 |
| NFR-05 | 并发、乱序或迟到结果 | 用 Case、Run和基线归属，不覆盖较新的用户结果 |
| NFR-06 | 服务重启或刷新 | 查询恢复已提交数据；未完成运行按检查点恢复或明确中断 |
| NFR-07 | 外部结果未知 | 保留Action和授权，先核实再重试，防止重复发送/创建 |
| NFR-08 | 存储或渲染失败 | 成果保存、文件生成、交付包就绪分别反馈，不显示虚假下载成功 |
| NFR-09 | 内容与上传安全 | 安全渲染HTML/Markdown，验证文件类型、大小、归属及危险内容 |
| NFR-10 | 成本、时间和重试上限 | 为Run及工具设置可见的合理边界，超限停止而非无限运行 |
| NFR-11 | 审计与可观察性 | 能关联请求、运行、能力版本、步骤耗时和错误，日志不过度泄露业务内容 |
| NFR-12 | 数据备份与恢复 | 恢复数据库及文件引用的一致状态，不能只恢复一半版本链 |
| NFR-13 | 可访问性 | 键盘可操作、图标有名称、焦点可恢复，状态不只靠颜色 |
| NFR-14 | 格式与跨端可读性 | 在支持设备和办公查看器中核对输出，不能把布局截断当成功 |
| NFR-15 | 模式隔离 | 示例、测试、真实运行及其数据有明确标记，真实失败不以mock兜底 |
| NFR-16 | 删除或来源不可用 | 明确显示证据不可访问及对新交付的影响，不伪造引用仍有效 |

### 18.2 性能体验目标

保留原 PRD 的可测量原则，但不将旧范围的整次运行时限直接套在所有完整业务上。

建议产品体验基线：普通列表/详情在声明的数据量与环境下服务端 p95不高于500ms；接收运行和返回标识 p95不高于2s；自动保存可沿用停止输入约800ms触发的初始体验目标。

这些是待实测目标，不是已实现成绩。大型文件、跨文件任务和外部连接应有清楚进度、超时与取消，不承诺所有任务在相同时长内完成。

计时需要区分排队、模型、工具、等待人/外部、渲染和上传；不得把用户等待批准计作模型持续执行，也不能隐藏失败重试的成本。

### 18.3 长期业务上下文

服务端保存业务事实、成果、草稿、版本与动作记录。用户视图偏好可本地保存，但必须以服务端授权和状态校验。

长期上下文不等于把全部历史聊天不断拼接给模型。系统应检索当前目标相关的材料、批准基准和未解决问题，同时提供原始记录回读能力。

### 18.4 可解释性

用户应能回答：这个数字从哪里来、为什么发生修改、哪些文件受影响、什么还没确定、哪个动作实际完成、谁批准了什么。

产品不展示或声称展示模型内部隐式思考；提供的是可验证的执行步骤、证据、工具输入输出和规则理由。

## 19. 完整业务场景

本章全部资料为合成验收场景，用于检验产品能否连续工作，不代表已发生的交易或真实生产周期。

### 19.1 场景 A：从询盘形成可报价材料

**输入**：德国客户要求3,000个定制背包，提供参考图片，目标为45天内抵达指定目的地，并提供初步交付条款；尚缺部分材料、尺寸与包装要求。

**用户操作**：“帮我把需求整理成工厂可以询价的资料。”

**系统必须**：建立或识别Case；提取有依据的参数；保留未知尺寸与材料；区分客户希望和已确认交期；生成需求简报、规格草稿、澄清问题与RFQ草稿。

**不能发生**：从图片捏造尺寸、把客户希望的45天当成供货承诺、把RFQ生成说成供应商已收到。

### 19.2 场景 B：供应商报价转成客户报价

**输入**：补充已确认规格，以及供应商A报价和企业成本规则。演示规定基础成本¥44、普通包装¥2、明确适用且已核实的其他单件成本¥4；汇率7.20 CNY/USD；目标毛利率20%；单价向上取至美分。

**用户操作**：“按这套规则核价并准备客户报价。”

**系统必须**：形成可编辑成本表，计算$8.69/件、商品金额$26,070.00；保留汇率和规则来源；生成客户版报价与回复；内部成本、底价和毛利不进入客户交付包。

**不能发生**：把未提供的税运费补零、把这套演示成本当作通用贸易成本模板、因报价生成而认为客户已经接受。

### 19.3 场景 C：包装变更与跨成果修订

**输入**：客户要求从普通包装改为定制彩盒。开始时只有客户请求，没有工厂新报价。

**第一轮系统行为**：记录变更；识别规格、RFQ、成本、报价、样品或生产资料可能受影响；生成影响报告、规格候选稿和工厂询问；不补出彩盒成本，不覆盖旧客户报价。

**第二轮输入**：供应商明确确认包装成本从¥2变为¥5，交期影响仍待核实。

**第二轮系统行为**：按原测试规则计算新报价$9.21/件、商品金额$27,630.00、增加$1,560.00；生成新成本、报价及回复草稿，保留交期待核实。用户审核可接受价格方案，但不能借此声称工厂交期不变。

**最后生效**：需要的商业和规格确认完成后，保存适用范围内的新发布记录；原已发送报价和历史批准保持可查。

### 19.4 场景 D：PO不一致与生产准备

**输入**：客户上传PO，但其中单价仍为旧版$8.69；生产资料计划使用新包装。

**用户操作**：“准备PI和生产资料。”

**系统必须**：指出PO与拟执行方案冲突；可制作差异报告和澄清草稿，不生成看似无条件有效的正式PI和生产放行。

客户补充更正PO与接受新方案的证据后，可生成金额$27,630.00的PI和相应生产准备材料。但若样品回复仍是“可以，不过LOGO再小一点”，生产规格批准条件尚未完成，系统不得显示“已获准量产”。

### 19.5 场景 E：工厂反馈与延期处理

**输入**：计划某物料于11月10日到厂，供应商新承诺改为11月17日；实际到位尚未证实。

**系统必须**：保留11月10日的原计划、新承诺及实际未知；按现有T&A依赖识别可能受影响节点；生成核实问题和备选方案。没有可验证产能与运输依据时，不给确定的赶工或到港保证。

**用户可完成**：批准一份对外沟通草稿，或选择向工厂核实替代方案。不能因为选择了方案就自动记录物料已到位。

### 19.6 场景 F：分批出运与单证

**输入**：客户已接受3,000件、$9.21/件的方案；首批实际装箱记录1,200件、每箱20件，共60箱，实际重量由装箱资料提供；余量1,800件尚未出运。

**系统必须**：首批装箱单为1,200件/60箱，相关商业金额按场景规则为$11,052.00；余量1,800件、对应金额$16,578.00。单证检查通过显式出运范围解释订单数量差异，不误报“订单3,000与装箱1,200不一致”。

若运输草稿误写70箱，系统定位到实际装箱依据并阻止该单证确认，而不是重新编造每箱数量来凑数。

### 19.7 场景 G：收款、投诉与结案

**输入**：客户提供付款通知，尚无到账核实；随后首批部分产品有投诉照片。

**系统必须**：付款显示“客户声称已付/待核实”，不显示已到账；建立关联首批、规格版本和历史确认的投诉证据包，生成需补信息及候选处理方案。

收到有效到账核实与售后处理批准后，可更新相应记录和制作沟通材料。关闭Case仍需明确原因；照片上传不等于责任已确定，补货草稿不等于补货已履行。

### 19.8 场景 H：从中途进入和长期续办

用户只有已有订单与装箱单，直接要求检查。系统应完成当前范围工作，不要求补建从询盘到打样的全部历史；但需标明缺少的上游确认对本次结论的限制。

关闭Tab或刷新后，回到同一Case能够看到当前Job、草稿、已发布基准、未解决问题和实际执行结果，无需重新解释完整背景。

## 21. 产品成效指标与验证方法

### 21.1 核心指标

**每位主操作者完成并实际采用的合格业务工作数，以及完成相同工作所需的人工净投入。**

不能单看生成文件数、Agent运行次数、打开Tab数量或模型调用量。用户可能需要的成果是一封准确澄清邮件，而不是十份不适用的文件。

### 21.2 指标定义

| 指标 | 定义与采集 | 防误读 |
| --- | --- | --- |
| 工作完成率 | 达到明确完成标准且通过用户验收的Job / 符合输入和授权条件的Job | “生成了草稿”不能冒充发送、确认或履约目标完成 |
| 首份可审核成果耗时 | 开始工作至形成首份通过对应检查的成果 | 分开模型耗时、等待人/外部及失败重试 |
| 人工净节省时间 | 相同范围手工耗时 − 使用工作台的输入、审阅、修正和返工耗时 | 不是只减掉模型生成时间 |
| 跨成果实质错误率 | 同业务口径不一致的字段/关系 / 被检查的有效关系 | 不将合法分批差异当错误 |
| 关键错误漏检率 | 被漏检的已知关键错误 / 植入或核实的关键错误 | 与普通文本错误分开统计 |
| 来源覆盖率 | 要求有依据的关键字段中，具有可用来源与正确范围的比例 | 引用了不相关文件不算覆盖 |
| 变更关联质量 | 应受影响成果的识别覆盖与误报情况 | 两者同时看，不能只追求多报 |
| 审阅负担 | 每项工作人工确认次数、复核时间及重复输入 | 避免每一步都确认导致省不了时间 |
| 采用率与返工率 | 被用于实际业务的成果、使用后需重新制作的比例 | 单纯下载不自动等于采用 |
| 非授权操作数 | 未授权发送、发布、敏感信息暴露等事件 | 应为零，单独作为安全指标 |
| 运行成本与失败恢复 | 每个合格工作成果的模型/工具成本及恢复代价 | 不以总调用成功率掩盖用户目标失败 |

### 21.3 验证方式

用匿名历史资料或明确合成场景回放同一工作，比较手工与工作台路径；加入真实类型的缺项、冲突和条件性批准，记录审阅与返工。

用户自报、内部回放和真实生产观测分别标记，不混为同一证据强度。未经真实验证不承诺提升成交率、降低成本或替代岗位的固定比例。

## 22. 配置、边界与待验证假设

### 22.1 可配置但不改变核心机制的内容

| 配置 | 示例 | 不得越过的底线 |
| --- | --- | --- |
| 产品/成果模板 | 背包规格、箱包BOM、企业PI、装箱单样式 | 模板不能绕过来源、范围和检查 |
| 计算与定价规则 | 毛利/加价、费用分摊、精度、汇率来源 | 金额仍可复算，未知不补零 |
| 审批用途与条件 | 报价、样品、生产、出运资料 | 不能让内部点击替代外部事实 |
| 语言、币种与单位 | 已验证的语言包、可用币种及换算 | 不承诺未支持语言准确或擅自换算 |
| 资源和连接 | 邮箱、文件空间、具体只读/写入工具 | 能力和权限逐动作检查 |
| 自动化策略 | 限定Case的新材料触发检查、明确日期提醒 | 用户授权、范围、取消和预算可控 |
| 交付受众与信息策略 | 客户版、供应商版、内部版 | 默认不泄露敏感成本和其他业务 |
| 文件、运行与保存限制 | 大小、数量、超时、保留期 | 限制提前可见，失败不伪装成功 |

### 22.2 不纳入产品固有目标的事项

完整CRM营销漏斗、通用获客平台、财务总账、工厂MES、通用物流实时追踪平台、无条件全行业合规结论、公开插件交易市场、任意系统终端自动操作和多人实时编辑平台，不是本产品为完成业务成果而必须内建的能力。

可以接入相应系统的具体工具或读取其证据，但不由此扩大为另一个庞大的管理系统。

### 22.3 已形成的产品决策

- EasyWork品牌、首页、多业务Tab、上下文隔离及默认双栏保留。
- 用户可从任意业务环节开始；不强制先建客户档案或Job表单。
- 七大能力域都纳入完整目标产品。
- 当前工作成果是主要操作对象，订单/询盘是上下文容器。
- 原子成功版本、独立草稿、确定性检查和可追溯历史继续成立。
- 引入按需Job、独立成果版本、ChangeSet、分项确认及用途发布。
- 新工作稿与已批准执行基准可以并存。
- 所有真实外部动作需要有效连接、权限与可核验结果。
- 运行的目标完成、文件保存、发布、交付和现实履约必须分别判断。
- 不以开发人数、排期或模块协作方式决定本版业务边界。

### 22.4 需要验证但不阻止定义的产品假设

**工作环境迁移意愿**：用户愿意在EasyWork编辑，还是主要在原有Excel/Word中编辑后回传？本版同时支持原生编辑与受控文件往返，不假定必须完全替换现有软件。

**企业模板差异**：真实箱包企业的规格、成本和PI模板是否能由有限配置覆盖？不假定一份通用模板适合所有企业。

**外部证据可获得性**：客户、工厂、运输、到账和现场检验资料能否低摩擦进入系统？无法取得的事实必须保持未知，而不是由产品愿景补齐。

**审阅密度**：哪些变更应合并审阅，哪些必须单独确认？通过使用测试平衡信任与操作负担，但不取消关键权限边界。

**商业价值**：哪些交付物和变更链带来最多净节省时间，用户是否愿意持续使用和付费？本文不杜撰市场规模、售价或客户成绩。

### 22.5 需要后续单独定义、但本PRD不代替的文档

机器可读数据与工具Schema、接口契约、具体UI设计、模板规范、运行环境和安全配置、自动化测试数据包及实施计划，应依据本PRD编写。

这些文档不得重新解释产品语义。例如接口不能把导出事件直接写成订单结束，前端不能把报价草稿显示成已获客户接受。

## 产品定义收束

**EasyWork 不要求用户先维护一个管理系统，再让 AI 帮忙。用户直接开始做事，系统在执行过程中形成必要的业务上下文、成果、版本和证据。**

**人负责目标、判断和重要承诺；Agent负责读取、制作、计算、检查、修订和经授权的交付。**

**工作台的稳定核心，是让每一次真实工作都可以接着上一次的可靠成果继续推进。**
